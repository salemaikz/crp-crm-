# CRM отдела продаж — правила для всех агентов и разработчиков

**Продукт SalemAI**: узкая CRM отдела продаж, которая ставится каждому клиенту
на его сервер в Казахстане. Одна компания — одна установка — своя БД. Модель
данных уже допускает несколько пространств (отделов) и воронок, но в
интерфейсе пока одно пространство продаж. Первый клиент — ЦРП. Всё, что
специфично для клиента, лежит в **пресете и настройках, а не в коде** (D-001).

Эти правила обязательны для Claude Code, Codex и людей. Специфика Claude
Code — в `CLAUDE.md`.

> **Нормативные документы** — `AGENTS.md`, решения со статусом «принято» в
> `docs/DECISIONS.md`, а также `docs/PROCESS.md`, `docs/ARCHITECTURE.md`,
> `docs/CONFIG.md`, `docs/INTEGRATIONS.md` в части, подтверждённой решениями.
> Они важнее кода: если код с ними расходится, это баг в коде — заводим issue
> и чиним код. Решение со статусом «предложено» действует как значение по
> умолчанию, но фактом не считается. **Описательные** документы (README,
> RUNBOOK, карта кода) при расхождении правятся под код. Пометка
> `[дозаполни]` означает, что факт не подтверждён.

## Источник задач — GitHub

- Любая работа = **issue** в приватном `salemaikz/crp-crm-`. Нет issue —
  сначала заведи, потом делай. Устные договорённости переносим в issue или
  `docs/DECISIONS.md`, иначе их не существует.
- Метки: поток `stream:platform|calling|base|booking|manager|ops`, уровень
  `tier:T0|T1|T2→T1|T2`, день `day:Д<N>`, `pilot`, `bug` с классом
  `P0|P1|P2`, `owner-decision`.
- Взял задачу — назначь себя и оставь комментарий «взял, ветка `<имя>`».
  Задача без отметки считается свободной.
- Одна задача → одна ветка → один PR с `Closes #N`.

## Как не пересекаться

1. В начале сессии прочитай `docs/PLAN.md` (§2 — потоки и зоны), открытые PR
   и issues своего потока и последний handoff в `docs/handoffs/`.
2. Меняй файлы **только в зоне своего потока**. Нужна правка чужой зоны —
   заведи issue на поток-владельца.
3. Общие файлы — по правилам `docs/PLAN.md` §2: миграции пишет только
   `architect` (имя `YYYY-MM-DD-<поток>-<slug>.sql`), `package.json` — через
   оркестратора, `docs/DECISIONS.md` — только `architect`, локали и манифест
   изоляции — по файлу на модуль.
4. Вливай в `main` маленькими PR хотя бы дважды в день, чтобы ветки не
   расходились.
5. В конце сессии — handoff (`/handoff` или шаги из
   `.claude/skills/handoff/SKILL.md`).

## Git

- `main` — стабильная ветка, напрямую не пушить. Работа идёт в ветках, слияние
  через PR после CI и `reviewer`.
- Ветки: `feat/<поток>-<тема>`, `fix/<поток>-<тема>`, `docs/<тема>`. Облачные
  сессии получают `claude/*` — остаёшься на ней и подтягиваешь `main`
  (`git fetch origin main && git merge origin/main`).
- **Conventional commits, тема по-русски**: `feat(calls): …`,
  `fix(access): …`, `docs(plan): …`. Скоуп — домен:
  `core`, `db`, `auth`, `access`, `config`, `fields`, `clients`, `cards`,
  `calls`, `pwa`, `distribution`, `intake`, `import`, `booking`, `deals`,
  `handoffs`, `tasks`, `timeline`, `reports`, `team`, `notify`, `admin`,
  `license`, `integrations`, `telephony`, `messenger`, `ui`, `i18n`,
  `presets`, `deploy`, `ci`, `ops`, `plan`, `agents`, `handoff`.
- Тело коммита объясняет, *зачем* сделано и какие компромиссы приняты, а не
  пересказывает дифф.
- Никогда: `--no-verify`, `push --force` в чужую ветку, переписывание истории
  `main`.

## Стек (D-006)

Next.js 16 (App Router, сборка `next build --webpack`, не Turbopack) · React 19
· TypeScript strict · Tailwind 4 · PostgreSQL 16 через `postgres` (postgres.js,
без ORM) · Zod · next-intl (`ru` сейчас, `kk` позже) · своя session-auth
(cookie + bcryptjs, **без JWT и NextAuth**) · web-push · тесты: node:test +
tsx (unit, интеграционные на Postgres 16), Playwright (e2e) · Docker Compose
на сервере.

Это **не тот Next.js, что ты знаешь**: перед кодом под Next 16 читай гайд в
`node_modules/next/dist/docs/`, потому что API и соглашения изменились.

## Слои кода (D-011)

`packages/core` (чистая логика, без БД и Next) → `src/server/platform` →
`src/server/domain` и `src/server/access` → `src/integrations` → `src/app`,
`src/ui`. SQL пишется только в `src/server/domain/*/repo.ts`. `SystemActor` —
только в `scripts/**` и `src/server/jobs/**`. Правила проверяют ESLint и
статические тесты, нарушение роняет CI.

## Код и данные

- **Специфика клиента — только в пресете.** В `src/`, `packages/`,
  `messages/`, `public/` и `src/app/manifest.ts` нет имени клиента, его
  терминов (названий мероприятий, ролей), города, лимитов, часов, итогов и
  цветов. Всё это лежит в `presets/` и настройках (`docs/CONFIG.md`); в
  локалях — только нейтральные шаблоны с подстановкой (`{eventShort}`).
  Статический тест ищет стоп-слова и роняет CI.
- **Источник лидов клиента в продукт не входит.** В коде, локалях, ответах API
  и журналах нет слов «парсер» и «сборщик» и нет кода источника. Есть только
  общий API приёма `ingest/v1` (`docs/INTEGRATIONS.md` §5).
- Пользовательский текст — только через `messages/ru/<модуль>.json` (позже
  `messages/kk/`). Строки в коде не хардкодить. Тест паритета ключей
  обязателен. Код языка — `kk` везде (`Intl`, `<html lang>`, файлы).
- БД: id `TEXT` (UUID), время `BIGINT` epoch-мс, деньги `BIGINT` в целых тенге
  (`amount_kzt`). Местная дата мероприятия — `TEXT 'YYYY-MM-DD'` плюс
  `starts_at`.
- Миграции — `migrations/YYYY-MM-DD-<поток>-<slug>.sql`: идемпотентные
  (`IF NOT EXISTS`), только добавляющие, учёт в `schema_migrations` с sha256
  файла. **Применённый файл не правится никогда** — только новый файл (D-059).
  Дизайн каждой миграции делает `architect`. Расширение закрытого списка
  `CHECK` считается добавляющей правкой. Колонка с ПДн помечается `-- pii` и
  вносится в реестр (`docs/ARCHITECTURE.md` §4.6).
- Пояс и календарь берутся из настроек установки. В чистых функциях `now`
  приходит параметром, `Date.now()` внутри ядра не вызывается.
- Небольшие модули, без мега-файлов. Комментарии в коде — по-русски, по делу.
- Перенос из SalemAI — только по белому списку `docs/ARCHITECTURE.md` §9.1, с
  шапкой `Источник: SalemAI 108fb70 <путь>`. Константы клиента уходят в
  настройки, реальные данные из тестов заменяются синтетикой.

## Доступ проверяется на сервере (D-016, D-017)

- Данные читаются и пишутся только через репозитории, первым аргументом идёт
  `viewer` или `SystemActor`. Охват (`scopeSql`) стоит в SQL каждого SELECT и
  UPDATE, а не в фильтре на клиенте.
- **Чужое = несуществующее**: 404 с тем же телом, что и для несуществующего id.
  Тексты ошибок не выдают, что запись есть.
- Каждый маршрут, server action и страница с данными (`page.tsx` с
  параметрами, `layout.tsx`, читающий данные) обёрнуты в
  `route()`/`page()`/`action()` и описаны в манифесте изоляции, иначе CI
  красный.
- Клиенту уходит только `projectFor(viewer, …)`: скрытых полей, чужих имён и
  лишних ПДн в ответе нет. В тексте push нет имён, номеров и названий.
- Директор — только чтение (423 на мутации). Администратор без роли в
  пространстве не видит карточки, не импортирует и не делает полную выгрузку;
  роль самому себе не назначает.

## Флаги

Новые модули выходят **за флагом** `FEATURE_*` и в бою остаются выключенными,
пока не прошли приёмку. На стенде флаги включены. Интеграции работают только
при одновременном выполнении трёх условий: флаг, признак в лицензии и
переключатель администратора (`docs/CONFIG.md` §8). Для зарубежных сервисов
нужно ещё письменное решение клиента о ПДн.

## Проверки перед пушем

`npx tsc --noEmit` · `npm run lint` · `npm run test:unit` · интеграционные
тесты затронутого модуля на Postgres 16 · `npm run test:isolation`, если
тронуты доступ, маршруты, роли или пресет · e2e своего потока на мобильном
размере. Падает — не пушим. Тест нельзя отключать, помечать `skip`/`only`
или ослаблять ради зелёного прогона. Исправление бага начинается с теста,
который падает до исправления. Полная стратегия — `docs/PLAN.md` §7.

## Безопасность и данные

- Репозиторий приватный, но **секреты и ПДн в него не попадают никогда**:
  `.env*` и `*.env` (кроме `*.example`), ключи лицензий, релизов и стенда, ключи age, токены,
  пароли, IP и доступы серверов, реальные имена, телефоны, компании, таблицы
  клиентов, коммерческие условия договоров.
- **Только синтетика.** Номера в тестах, фикстурах, документах и примерах —
  `+7 709 …` (код не выдан ни одному оператору), компании выдуманные.
- ПДн граждан РК хранятся только на серверах в РК (D-008). Передача в
  зарубежные сервисы (Wazzup, Zadarma, push-шлюзы) — только после решения
  клиента и с согласия, push — без ПДн.
- **ПДн с боевого сервера не передаём в ИИ-сессии**: ни в промпты, ни в логи,
  ни в файлы. Логи для разбора — только обезличенная выдержка.
- **У ИИ-агентов нет доступа к боевым серверам.** Агенты работают локально и
  на стенде. На бой ставит владелец командой `crmctl update` (`docs/DEPLOY.md`).
- Вебхуки и приём лидов: проверка подписи или ключа, идемпотентность,
  повторная доставка ничего не задваивает. Итоги, записи и покупки
  идемпотентны.
- Образ для клиента — без `src/`, `*.ts`, `*.map`. Карты кода не включать
  никогда.
- Лицензия никогда не блокирует данные клиента: в любом состоянии работают
  просмотр, полная выгрузка и **мутации безопасности** — отключить сотрудника и
  закрыть его сессии, «выйти везде», сброс пароля, обезличивание, отзыв ключей
  приёма и вебхуков, выключение интеграции (D-054).

## Бренд и интерфейс

Минималистичный интерфейс: оператор работает с телефона (нижнее меню, одна
карточка, крупная зелёная кнопка), менеджер — с ноутбука (боковое меню). Цвета,
логотип и название берутся из темы в настройках клиента. Логотип клиента не
перерисовывается и не искажается.
