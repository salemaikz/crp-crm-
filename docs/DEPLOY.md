D-027…D-031, D-035, D-044…D-046, D-054, D-059…D-064 в `docs/DECISIONS.md` и

Пошаговые команды появятся в `docs/ops/RUNBOOK.md` (задачи O2, O3). Здесь —
что ставим, где, как обновляем и как защищаем.

## 1. Коротко

- **Боевой сервер** — ВМ HyperCloud (облако группы Beeline, ЦОД в Алматы),
  аккаунт и root у ЦРП. На нём CRM, PostgreSQL, источник лидов ЦРП в отдельном
  контейнере и nginx.
- **Второй сервер** — у другого провайдера в РК: стенд с синтетикой,
  зашифрованные копии боевой БД и внешний мониторинг. Рекомендация: на
  аккаунте SalemAI (D-044).
- На сервер ЦРП приходят **готовые образы**, без исходников и карт кода.
  Обновляет владелец командой `crmctl update`. У ИИ-агентов доступа к боевому
  серверу нет.
- **HyperCloud не принимает оплату картой**: работа идёт по договору,
  постоплатой по ЭСФ. Быстрый путь — бесплатный тестовый период до 30 дней по
  письму, ответ до 2 рабочих дней. Письмо — сегодня.

любой момент, а полная выгрузка в CRM доступна всегда. Отвергли: второй сервер
на ТОО ЦРП — тогда сборки стенда достаются root клиента; третий сервер
отдельно под копии — +8 200 ₸/мес, вернёмся к этому при втором клиенте.

## 3. Что стоит на серверах

### 3.1. Боевой сервер

```
Интернет ──443──► nginx (хост, certbot, CSP, HSTS; /api/ingest/ закрыт снаружи)
                     │ 127.0.0.1:3100
            ┌────────▼─────────── compose-проект «crm» ───────────────────┐
            │  app (Next standalone, 1 процесс) ◄─┐                       │
            │  worker (тот же образ: расписание, inbox/outbox)            │
            │  migrate (разовый, роль crm_owner)  │                       │
            │  db: postgres:16, том crm_pg,       │ сеть crm_internal     │
            │      роли crm_owner и crm_app       │                       │
            └─────────────────────────────────────┼───────────────────────┘
                                                  │ внешняя сеть crm_ingest (видит только crm-app:3000)
            ┌─────────────── отдельный compose-проект владельца ──────────┐
            │  источник лидов ЦРП (скомпилирован Nuitka, своя лицензия)    │
            │  своя БД и роль, свой том; слушающих портов нет              │
            └──────────────────────────────────────────────────────────────┘
cron хоста: копии, healthcheck, certbot, чистка образов
```

| Что | Как |
|---|---|
| ОС | Ubuntu 24.04 LTS, часы через chrony, пояс хоста UTC. Пояс приложения `Asia/Almaty` берётся из настроек; при старте проверяется tzdata |
| Доступ | SSH только по ключу, вход root по паролю выключен, fail2ban; ufw и группы безопасности HyperCloud: наружу открыты 22, 80, 443 |
| Учётки | root — у ЦРП. Учётка владельца `crmops` с sudo **только** на `/usr/local/bin/crmctl` (D-027, PLAN §9 В-15). Агентов на боевом сервере нет |
| Docker | Docker Engine и compose plugin. Порты контейнеров наружу не публикуются: только `app` на `127.0.0.1:3100` (Docker обходит ufw, поэтому порты не публикуем вовсе) |
| Сети | `crm_internal` — app, worker, db. `crm_ingest` — **внешняя** сеть, её создаёт `install.sh` (пересоздание проекта CRM не отключает чужой проект); в ней у активного `app` псевдоним `crm-app`, источник лидов ходит только на него. Источник не видит БД CRM и `crm_internal` |
| Источник лидов ЦРП | отдельный проект владельца в своём приватном репозитории; лимит памяти 512 МБ, CPU 1; выход в интернет только к своему порталу и Telegram; слушающих портов нет; отчёты и тревоги — владельцу, только цифры. Ключ приёма выдаётся `crmctl ingest-key` после ответа юриста (INTEGRATIONS §6). Предел защиты от root — §8.3 |
| Пути | `/etc/crm/*.env` (root, 0600) — окружение; `/var/lib/crm/license/` — лицензия; `/var/lib/crm/packages/` — пакеты релизов; `/var/backups/crm/` — две последние копии; `/var/log/crm/` — журналы, хранение 14 дней, без номеров и тел запросов |
| nginx | шаблоны crp-kz: CSP, HSTS, без `X-Powered-By`, журнал без query string и Referer; `/api/ingest/` закрыт снаружи, пока `INGEST_PUBLIC=0`; страница обслуживания на время обновления |
| Лимиты | `db`: `shared_buffers` 1,5 ГБ, `max_connections` 50, `log_parameter_max_length = 0`. `app`: куча Node до 1 ГБ. Один процесс `app`, потому что лимиты входа хранятся в памяти (D-032) |

**cron хоста** (время сервера UTC; Алматы = UTC+5)

| Задача | UTC | Алматы |
|---|---|---|
| Копия БД | 21:00 ежедневно; в пилот до 15.11 ещё каждый час 04:00–14:00 | 02:00; в пилот ещё каждый час 09:00–19:00 (D-031) |
| Проверка восстановления из копии | вс 22:00 | пн 03:00 |
| `healthcheck.sh` | каждые 5 минут | — |
| `certbot renew` | 03:15 ежедневно | 08:15 |
| Чистка старых образов (оставить текущий и прежний) | вс 23:00 | пн 04:00 |

Расписание приложения (раздача, сводки, «серые» БК) — в контейнере `worker`,
а не в cron (D-018). Копии и мониторинг — в cron хоста: они должны работать,
даже когда контейнеры лежат.

### 3.2. Второй сервер

| Что | Как |
|---|---|
| Стенд | тот же compose-проект `crm`, адрес на домене SalemAI под basic auth, только синтетика (+7 709 …), флаги включены, лицензия с пометкой `stage`. Обновляется из CI пакетом, подписанным ключом `stage`, через `crmctl update` — **автоматически в 20:00 и по кнопке**; на время сессий с людьми (23.10 15:00–17:00, 27.10 09:00–10:30, 28.10 17:00–18:00) заморожен (D-030) |
| Копии ЦРП | каталог `/srv/backups/crp/` на **отдельном томе**, владелец — отдельный пользователь `backup`; том не монтируется ни в один контейнер стенда, у пользователей стенда и CI нет к нему прав. Писать туда может только ключ боевого сервера: `rrsync -wo -no-del -no-overwrite` — запись без чтения, удаления и перезаписи. Хранение 7 дневных и 4 недельных копий — cron пользователя `backup`. Остаточный риск: компрометация root второго сервера через сборку стенда; полное закрытие — объектное хранилище в РК с блокировкой удаления или отдельный сервер под копии (при втором клиенте) |
| Внешний мониторинг | раз в минуту проверяет `https://crm.<сайт ЦРП>/api/health`; после трёх неудач подряд — тревога в Telegram |
| Доступ | владелец по ключу; CI — отдельный ключ, который умеет только `crmctl update` на стенде (forced command, без shell и без доступа к тому копий). ИИ-агенты работают только со стендом |

Реальных данных на стенде нет никогда. Учебное восстановление боевых копий
делается не на стенде, а на боевом сервере во временную БД или на временной
ВМ в РК (раздел 6.3).

## 4. Установка с нуля

Порядок (команды — в RUNBOOK, задача O2):

1. ЦРП: ВМ выдана, root у ЦРП, создана учётка `crmops` с ключом владельца и
   sudo только на `crmctl`. DNS: А-запись `crm.<сайт ЦРП>`, TTL 300.
2. Владелец копирует на сервер пакет `crm-crp-<версия>.tar.zst` и
   `install.sh`; root ЦРП один раз запускает `install.sh`. Скрипт ставит
   Docker, nginx, certbot, ufw, fail2ban, chrony, `crmctl`, cron, шаблоны
   окружения и внешнюю сеть `crm_ingest`.
3. `crmctl install <пакет>`: проверка подписи пакета, загрузка образов,
   создание ролей БД `crm_owner` и `crm_app`, миграции, применение слоёв
   пресета `base`, `kz`, `consulting-sales` и накладки клиента (с ассетами),
   генерация `installId`, ключей HMAC и AES (печатаются **один раз** — владелец
   сразу сохраняет копию вне сервера и передаёт директору запечатанный
   конверт), первый администратор.
4. Владелец получает `installId` (печатается в шаге 3), у себя подписывает
   лицензию под него (`scripts/license-sign.ts`, ≈ 10 минут) и ставит её
   `crmctl license install <файл>`. Заранее, до установки, лицензию выпустить
   нельзя. До этого шага установка в `missing` («только чтение»).
5. Сертификат certbot, проверка `https://…/api/health`, вход с двух телефонов.
6. Открытые ключи age двух хранителей → `/etc/crm/backup-recipients`; ключ
   SSH для отправки копий на второй сервер; тестовая копия → `offsite: true`.
7. Telegram-бот тревог: токен и чат в `/etc/crm/monitor.env`.
8. Приёмка ВМ по разделу 10.

## 5. Выкладка и откат

### 5.1. Путь изменения

```
PR ──► CI: tsc, lint, unit, интеграционные (Postgres 16), изоляция, e2e потока
   ──► reviewer ──► main ──► CI: образ, проверка образа, пакет (подпись stage)
   ──► стенд (crmctl update: автоматически в 20:00 и по кнопке) ──► ночью e2e и изоляция на пакете
тег vX.Y.Z (защищён; release-workflow в Environment с одобрением владельца)
   ──► CI: образ клиента (водяной знак) + пакет crm-crp-X.Y.Z.tar.zst без подписи + sha256
   ──► стенд: тот же пакет, подписанный stage → полный e2e и изоляция
   ──► владелец: сверка sha256, подпись у себя (release-sign) ──► scp на бой ──► crmctl update
```

На бой ничего не уходит из CI автоматически: у CI нет ключей боевого
сервера и нет ключа, которому доверяет боевой `crmctl`; у root ЦРП нет
доступа к репозиторию и реестру образов (D-027, D-064). Теги `v*` защищены,
ИИ-сессии их не ставят.

### 5.2. `crmctl update <пакет>`

1. Проверить подпись `manifest.sig` (Ed25519; бой принимает только ключи
   релизов владельца, стенд — ещё и `stage`) и что версия схемы не ниже
   текущей.
2. Загрузить образы (`docker load`) и проверить действующую лицензию **новым**
   образом: `invalid` (другой водяной знак, неизвестный `kid`) — стоп до
   переключения, прежняя версия продолжает работать.
3. Если есть новые миграции — сначала копия БД; без успешной копии обновление
   останавливается.
4. `migrate` под `crm_owner`: SQL-миграции (только добавляющие,
   идемпотентные, под advisory lock, сверка sha256 применённых файлов —
   D-059) и миграции настроек (новая ревизия, старая остаётся — D-060).
5. Поднять новый `app` рядом со старым, проверить `/api/health`
   (версия, миграции, лицензия), переключить nginx и псевдоним `crm-app` в
   сети `crm_ingest`, остановить старый. Тест обновления идёт с подключённым
   фиктивным источником лидов: после переключения приём продолжает работать.
   Пользователь видит перезагрузку страницы, итоги ждут в outbox телефона.
6. Через 2 минуты проверить снова. Сбой → автооткат на прежний тег.

`crmctl rollback` — около минуты. БД не откатывается: миграции только
добавляющие, и прежняя версия работает на новой схеме и на своей ревизии
настроек (это проверяет CI, D-060); правки настроек, сделанные новой версией,
после отката не видны — `rollback` об этом предупреждает.

### 5.3. Когда выкладываем в пилот (D-046)

| Что | Когда |
|---|---|
| Обычный патч | 19:00–21:00, после конца смены |
| P0 (утечка, потеря итогов, нельзя войти или звонить) | сразу, с предупреждением в чат ЦРП за 5 минут |

## 6. Копии и восстановление

### 6.1. Как делаются

- `pg_dump -Fc` из контейнера `db` → `age` на открытые ключи двух хранителей
  (владелец и директор ЦРП) → файл с `.sha256`. Закрытых ключей на серверах
  нет.
- Две последние копии остаются на боевом сервере для быстрого восстановления,
  остальные уходят на второй сервер через `rsync` (только запись). В пилот
  (до 15.11) часовые копии рабочего дня тоже уходят на второй сервер; там
  хранится последняя часовая и все ночные.
- В копию входит вся БД CRM, включая `license_state` и `installId`. **Ключи
  окружения** (HMAC, AES, VAPID) в копию не входят: они хранятся у владельца
  офлайн и в конверте у директора. Без них стоп-лист и секреты интеграций не
  читаются.
- БД источника лидов — забота его проекта и в эти копии не входит.
- Статус копии (`ok`, время, размер, `verified`, `offsite`) пишется в файл
  статуса, его читает healthcheck.

RPO в пилот — не больше часа в рабочее время (копии каждый час 09:00–19:00 и
в 02:00), после пилота — сутки (D-031, вопрос В-19 PLAN). Обезличенные по
запросу субъекта данные исчезают из копий не позже чем через 35 дней (7
дневных + 4 недельные).

**Ключи окружения.** Файлы окружения называются `*.env` (`/etc/crm/app.env`,
`/etc/crm/monitor.env`). В репозитории — только `*.env.example` без значений;
`*.env`, `*.key`, `id_*`-ключи SSH и `*-private*` закрыты `.gitignore` и запретами чтения агентам
(`.claude/settings.json`).

### 6.2. Автоматическая проверка восстановления

Каждую неделю копия восстанавливается во временную БД `crm_restorecheck` ещё до
шифрования. Затем сверяются число таблиц, последняя миграция и счётчики строк,
и БД удаляется. Ключ хранителя для этого не нужен. Итог попадает в статус
`verified`.

### 6.3. Учебные восстановления (цель — не дольше 30 минут)

| Дата | Где | Что проверяем |
|---|---|---|
| Чт 22.10 | CI или локальный Docker, синтетика (от второго сервера не зависит) | сама процедура и скрипты |
| Пн 26.10 | бой, временная БД | расшифровка ключом хранителя, сверка счётчиков после импорта |
| Пт 30.10 | чистая временная ВМ в РК | «сервер погиб»: установка, окружение из копии владельца, последняя копия со второго сервера, вход; затем ВМ удаляется |
| далее | бой, временная БД | раз в месяц, отметка в журнале учений у владельца |

Восстановление с реальными данными никогда не делается на стенде и не
выполняется ИИ-агентом.

## 7. Мониторинг

`healthcheck.sh` (из crp-kz) на боевом сервере раз в 5 минут. Тревога уходит
только при смене состояния. Текст содержит имя проверки, имя установки и
время, без IP и ПДн.

| Проверка | Порог |
|---|---|
| `app_health` | `/api/health` не `ok` или отвечает дольше 5 с |
| `containers` | `app`, `worker` или `db` не запущены; больше 3 перезапусков за час |
| `worker_ticks` | раздача не отработала свой слот в рабочее время |
| `backup` | копия не `ok` или старше 26 ч (в пилот в рабочее время — 2 ч) |
| `backup_offsite` | копия не ушла на второй сервер двое суток |
| `disk` | свободно меньше 20 % — предупреждение, меньше 10 % — авария |
| `tls_cert` | меньше 21 дня — предупреждение, меньше 7 — авария |
| `license` | `expiring`, `expired`, `read_only`, `invalid` |
| `external` (со второго сервера) | `https://crm.<сайт ЦРП>/api/health` недоступен 3 минуты |

Куда: Telegram-бот на ТОО ЦРП, чат с администратором ЦРП и владельцем
(сопровождение по договору, D-035). Телеметрии разработчику нет.

Тревоги источника лидов («сколько собрано», «сколько отправлено», «ошибка
портала») шлёт сам источник, только владельцу и только цифрами. В CRM их нет.

## 8. Защита кода и лицензия

### 8.1. Как собирается образ (D-028)

1. `packages/core` (вся ценная логика: состояния, раздача, дедуп, импорт,
   запись, права, проверка лицензии) → esbuild в один файл →
   `javascript-obfuscator` (переименование, перестановка потока, без тяжёлого
   шифрования строк). Подключается к Next как внешний серверный пакет.
   **K0 сошёлся (D-101)**, по факту:
   - `npm run build` = `node packages/core/build.mjs && next build --webpack`;
     ядро → `packages/core/dist/index.cjs` (CJS, без карт; `zod` не бандлится).
     `node packages/core/build.mjs --check` дополнительно гоняет тесты ядра и
     тест-векторы на обфусцированном коде.
   - `@crm/core` — рабочее пространство npm; в production-сборке Next
     оставляет `require('@crm/core')`, Node находит ядро через ссылку
     `node_modules/@crm/core → packages/core` и `exports` → `dist/index.cjs`.
     В dev и тестах — исходники (paths в `tsconfig.json`).
   - В `.next/standalone` ядро — только `packages/core/{package.json,
     dist/index.cjs}` и ссылка `node_modules/@crm/core`; `src/`, `*.ts` и
     `.map` нет. При копировании в образ ссылку сохранять (Docker `COPY` её
     сохраняет).
   - Импорт ядра — только `@crm/core` и только в серверном коде Node.js:
     подпуть, клиентский компонент или edge роняют `next build`.
   - Воркер и `crmctl` (esbuild) тоже держат `@crm/core` внешним, иначе ядро
     попадёт в их файлы без обфускации и без водяного знака клиента. Это делает
     `scripts/crmctl/build-cli.mjs`: `@crm/core` в бандле — ленивая прокладка над
     `require('@crm/core')`, ядро берётся из образа (`node_modules/@crm/core →
     packages/core/dist`), то есть проверка лицензии в `dist/crmctl.mjs` идёт
     ключами образа. Хостовая копия `crmctl.mjs` (`install.sh` берёт её из образа)
     запускается без ядра: всё, что требует ядра, исполняется внутри образа
     (`docker run … crmctl license verify`).
   - Ключи лицензий: `build.mjs --license-keys <файл>` (JSON `kid → открытый
     ключ`) вшивает `__CRM_LICENSE_KEYS__`; вместе с `--customer` обязателен,
     тестовые `test-*` в сборке клиента запрещены. В Dockerfile — секрет
     `license_keys`, аргументы `CUSTOMER_ID`, `BUILD_ID`.
   - Замеры: сборка ядра — доли секунды (≈ 0,7 с на 100 КБ минифицированного
     кода); `next build` ≈ 31 с, как без ядра; файл ядра больше в 1,2–2,2 раза;
     горячий путь медленнее ≈ на 15–20 %.
   - Запасной вариант D-028 без правки кода: `CRM_CORE_BUNDLE=1 npm run build`
     — ядро бандлится из исходников и только минифицируется.
2. `next build --webpack`, `output: 'standalone'`,
   `productionBrowserSourceMaps: false`. Воркер и `crmctl` собираются esbuild с
   минификацией.
3. В образ попадают только `.next/standalone`, `.next/static`, `dist/*.mjs`,
   `migrations/*.sql`, пресеты `base` и отраслевые. Шаг CI ищет в образе
   `src/`, `*.ts`, `*.map`, `.git`, `tests/` и роняет сборку, если что-то нашёл.
4. Слой клиента: тот же образ плюс ядро, собранное с `CUSTOMER_ID` и
   `BUILD_ID` (`build.mjs --customer <id> --build-id <id>`); слой заменяет
   один файл `packages/core/dist/index.cjs`, `next build` не повторяется
   (проверено в K0). **Водяной знак** стоит в нескольких местах ядра и в метке
   образа. Таблица `BUILD_ID → клиент` хранится у владельца вне репозитория
   продукта (D-034).
5. Пакет `crm-<клиент>-<версия>.tar.zst`: образы, `compose.yml`,
   `manifest.json` (digest образов, версии схемы и настроек), `manifest.sig`.

В пилот 27.10 идёт `0.9.0` — минифицированный образ без исходников и карт, с
лицензией и водяным знаком. С 28.10 стенд, а с вечера 29.10 и бой переходят на
пакет `0.9.x` с обфусцированным ядром; полный e2e и прогон изоляции идут **на этом
подписанном пакете**, поставленном на стенд через `crmctl update`, поэтому
1.0.0 выходит на артефакте, который пилот уже проверил (D-028). Выпуск без
обфускации — только с письменного согласия владельца (PLAN §9 В-1).

### 8.2. Лицензия (D-029)

- Файл `CRM1.<payload>.<подпись>`, Ed25519. В нём: клиент, `installId`,
  модули (`features`), места (`seats`), срок, льготный период.
- Подписывает владелец **офлайн** утилитой `scripts/license-sign.ts` под
  `installId` конкретной установки. Закрытые ключи лицензий и релизов не лежат
  ни в репозитории, ни в CI (D-064).
- Проверка без сети при старте и раз в час. «Сейчас» = максимум из часов и
  последнего виденного момента: перевод часов назад не продлевает срок.
  Вперёд последний виденный момент сдвигается не больше чем на 48 ч за
  проверку; больший скачок — тревога «часы сервера ушли вперёд». Если ложный
  момент уже записан, владелец выдаёт лицензию с подписанным `clockResetTo`
  (D-029).

| Состояние | Что видит ЦРП |
|---|---|
| за 14 дней до срока | баннер администраторам |
| срок прошёл, идёт льготный период | баннер всем, всё работает |
| льготный период кончился | «только чтение»: просмотр, вход, **полная выгрузка**, загрузка новой лицензии и **мутации безопасности** (отключить сотрудника, «выйти везде», сброс пароля, обезличивание, отзыв ключей, выключение интеграции — D-054); раздача и рассылки стоят; приём лидов отвечает «не принимаем» |
| подпись не сходится или чужая установка | после работавшей лицензии — баннер и 7 дней льготы, затем «только чтение»; при первой установке — сразу «только чтение»; сообщение администратору и в Telegram |

Данные не удаляются, не шифруются и не блокируются для выгрузки никогда.
Пилотная лицензия — до 30.11 и 30 дней льготы (рекомендация, PLAN §9 В-7).

### 8.3. Честная граница

root сервера ЦРП видит контейнеры, файлы образа, БД и сетевой трафик. Полной
защиты от root нет. Цель — сделать копирование дороже лицензии и доказуемым:
нет исходников и карт кода, обфусцированное ядро, водяной знак клиента,
подписанная лицензия и договор («лицензия, а не права на код; запрет
копирования, декомпиляции и передачи»).

**Источник лидов ЦРП на этом же сервере** защищён так же ограниченно, и это
нужно знать заранее (вопрос В-4 PLAN): root ЦРП может выполнить
`docker exec` в его контейнер, снять дамп его БД (запас базы, который
владелец называет своим заработком), прочитать его окружение (доступы к
порталу, токен Telegram, ключ приёма) и скопировать бинарник Nuitka.
Смягчение: источник хранит в своей БД минимум и удаляет отправленное после
ответа CRM; держит запас только на горизонт (D-057), а не всю собранную базу;
своя лицензия с коротким сроком (останавливается только источник); слушающих
портов нет. Полностью закрывает это только размещение источника на сервере
владельца в РК — тогда он ходит в CRM по HTTPS с ключом и ограничением по IP.

## 10. Приёмка ВМ в тестовый период

1. `pg_test_fsync` и `fio` на NVMe: задержка fsync и IOPS.
2. `sysbench cpu`, `stress-ng` и `steal` в `top`: насколько ядра общие.
3. `mtr` из офиса ЦРП в Астане и с телефонов операторов через мобильные сети.
4. Нагрузка 20 одновременных пользователей (сценарий из `tests/load/`): после
   неё остаётся свободной не меньше 25 % памяти.
5. Полное восстановление из копии ≤ 30 минут.
6. Перезагрузка ВМ: всё поднимается само, health ok, тревога пришла ровно два
   раза (упал — поднялся).
7. `certbot renew --dry-run` проходит; заголовки CSP и HSTS на месте.
