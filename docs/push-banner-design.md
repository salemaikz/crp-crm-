Решения: D-327 (баннер), D-328 (push: привязка к сессии, включение, текст), D-329 (протокол без пакета,

## 1. P10b — баннер лицензии (D-327)

### 1.1. Данные

Источник один — `currentLicenseSnapshot()` (`src/server/platform/license/current.ts`): кэш на процесс,
пересчёт не чаще раза в минуту. Баннер не делает новых запросов к БД на страницу: тот же снимок уже
читают обёртки доступа (`viewer.license`). Новых таблиц и колонок нет.

Чистая функция `licenseBanner(snap, who, now)` в `src/ui/shells/licenseBanner.ts` (без БД, тест на
таблицу ниже) возвращает `null` или `{ tone: 'info' | 'warn' | 'danger', key, params }`, где `params` —
только числа и даты (`days`, `date` в поясе установки). Внутренних кодов (`wrong_build`, `clock`,
`error`, `fileReason`, id лицензии, установки) в ответе нет.

### 1.2. Кому и что

| Состояние снимка | Администратор (`viewer.isAdmin`) | Остальные |
|---|---|---|
| `valid` | нет | нет |
| `expiring` (`status`) | `warn`: «Лицензия заканчивается {date}, осталось {days} дн. Продлите у поставщика» | нет |
| `expired`, идёт льгота (`access = grace`) | `danger`: «Срок лицензии истёк. Работа продолжается до {date}, затем только просмотр» | нет |
| `invalid` с льготой (`wrong_build`, `access = grace`) | `danger`: «Лицензия не подходит к этой версии. Работа продолжается до {date}. Обратитесь к поставщику» | нет |
| `read_only`, `reason = clock` | `danger`: «Часы сервера отстают. Пока их не исправят, CRM работает только на просмотр» + ссылка на ADMIN.md §«Лицензия» | `info` коротко: «Сейчас только просмотр. Обратитесь к администратору» |
| `read_only` (срок и льгота прошли), `invalid` без льготы, `missing`, `error` | `danger`: «Только просмотр: лицензия недействительна. Выгрузка и управление доступом работают. Обратитесь к поставщику» | `info` коротко: то же, что выше |

Директор и роль «только чтение» баннер `read_only` не получают: они и так только читают.

### 1.3. Где

Серверный `RoleShell` получает снимок вместе с меню (`Promise.all`) и передаёт в `AppShell` готовый
`banner` (текст уже переведён). `AppShell` рисует полосу над содержимым страницы, под шапкой: на телефоне —
во всю ширину над карточкой, на ноутбуке — над областью страницы справа от бокового меню. Полоса не
закрывается навсегда: администратор может свернуть её до следующей загрузки (состояние в памяти
страницы, не в хранилище). Цвета — токены темы (`--warn`, `--danger`), текст — `messages/ru/shell.json`
`license.*`. Мутация, получившая 423, по-прежнему показывает своё сообщение — баннер его не заменяет.

### 1.4. Тесты

Unit — таблица 1.2 целиком (`licenseBanner`), включая «нет внутренних кодов в params». E2e pixel-7 —
стенд с лицензией `expiring` (ключ стенда) — администратор видит полосу, оператор нет.

## 2. P8b — web-push (D-328, D-329)

### 2.1. Что уже есть (schema v1)

`notifications` пишут модули; `push_subscriptions (endpoint UNIQUE, p256dh, auth, device_id, disabled_at)`,
`push_outbox (notification_id, subscription_id) UNIQUE, state, attempts, next_at, lease_until`; очередь
воркера `push_outbox` (аренда, повторы, `writes: business` — при «только чтение» не рассылает), включена
только при `FEATURE_PUSH`.

### 2.2. Миграция `2026-10-27-manager-push.sql` (без неё никак)

1. `push_subscriptions.session_id TEXT` — sha256 токена сессии (`sessions.id`), без FK: строка сессии
   удаляется при выходе, подписка остаётся до чистки. **Почему нужна:** на общем телефоне браузер держит
   одну подписку на устройство. Без связи с сессией сервер не знает, вышел ли сотрудник на этом
   телефоне: при выходе без сети, «выйти везде», отключении сотрудника push продолжал бы приходить
   следующему человеку. Со связью правило одно: push уходит, только пока жива сессия, которая
   подписала устройство.
2. `push_settings` — одна строка: `enabled`, `crossborder_approved_at/by`, `updated_at/by`.
   Это отметка решения клиента о зарубежных push-сервисах и переключатель администратора (как
   `integrations`, но без плагина: у push нет провайдера, секретов и вебхуков).

Права: `push_settings` получает SELECT/INSERT/UPDATE по умолчанию (`grants.sql`), DELETE не нужен.

### 2.3. Когда push работает

Одновременно: `FEATURE_PUSH=1` ∧ ключи VAPID в окружении верны (`VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`,
`VAPID_SUBJECT`, приватный сходится с публичным) ∧ администратор включил ∧ отмечено решение клиента ∧
лицензия не «только чтение» (очередь `business`). Иначе подписка не принимается (`400 push_off`), очередь
не наполняется, а уже стоящие строки при отправке отменяются (`cancelled`). Выключение — мутация
безопасности (`integration.disable`, D-054). Признака в лицензии нет: push — часть базового продукта.

### 2.4. Подписка и отписка

- `GET /api/push` (сессия) → `{ available, publicKey, bound }` — показывать ли кнопку «Уведомления на
  телефон» и есть ли действующая подписка, привязанная к **текущей** сессии. `available` ложно и для
  роли «только чтение» (директор): подписка для неё — мутация, сервер ответил бы 423.
- **После входа** (`PushSync` в оболочке) и на экране профиля: разрешение дано, подписка в браузере есть, а
  `bound` ложно — страница шлёт `subscribe`, и подписка переходит к новой сессии. Признак берётся с сервера,
  а не из хранилища вкладки: «выйти везде», простой `idleHours`, сброс пароля меняют сессию без обычного
  выхода. «Уведомления включены» в профиле — только при `bound`.
- `POST /api/push/subscribe` (сессия) — `{ endpoint, p256dh, auth, deviceId }`. Сервер проверяет адрес по
  закрытому списку хостов push-сервисов (https, без порта и учётки; D-329 — защита от запросов сервера на
  произвольный адрес), ключи по длине и точке кривой. Upsert по `endpoint`: владелец, ключи и `session_id`
  перезаписываются, `disabled_at` снимается. Устройство сменило владельца — его стоящие строки очереди
  отменяются. У сотрудника не больше 10 действующих подписок (лишние — старейшие — выключаются).
- `POST /api/push/unsubscribe` (сессия, мутация безопасности `auth.logout`) — `{ endpoint? }`: выключаются
  подписки этой сессии и подписка с этим адресом, если она своя; их очередь отменяется.
- **Выход** (`src/ui/call/logout.ts` → `src/ui/push/device.ts`): первым шагом, до сети, страница снимает
  подписку в браузере (`PushSubscription.unsubscribe()`), затем шлёт `unsubscribe` с её адресом
  (`keepalive`, не ждёт успеха).
  Сервер всё равно не отправит: сессии больше нет (§2.5). Service worker не показывает push, пока висит
  метка `crm-logout-pending`.

### 2.5. Наполнение и отправка

Наполнение — шаг очереди перед взятием пачки (`QueueSpec.fill`, раз в 5 с): закрытый список видов
(`PUSH_KINDS`) × действующие подписки получателя с живой сессией (`sessions.id = session_id`,
`expires_at > now`, сотрудник активен, пароль задан). Простой `idleHours` не учитывается: утренняя
сводка дойдёт до телефона, на котором вчера не вышли, но открыть её можно только после входа (текст без
ПДн). Берутся непрочитанные уведомления не старше 30 мин и не старше подписки. `next_at` — с учётом тихих
часов (`notifications.quietHours` пространства по умолчанию → ближайший рабочий момент календаря).
`payload` — `{ kind, n: {числа} }`: строки из `params` отбрасываются при записи.

Отправка (обработчик `push`): перед запросом строка сверяется заново — уведомление не прочитано,
получатель = владелец подписки, подписка не выключена, сессия жива, push включён, задержка не больше 6 ч;
иначе `cancelled`. Текст строится здесь из `messages/ru/push.json` по виду: только числа (свой
маленький форматтер с `plural`, без строковых подстановок). Тело — `{ title, body, tag, url: '/notifications' }`,
шифрование aes128gcm, VAPID ES256, `TTL` 12 ч, `Topic` = вид (новое заменяет недоставленное старое).
Ответ сервиса: 2xx → `sent`, `last_ok_at`; 404/410 → подписка выключена, строка `cancelled`; 429/5xx/сеть →
повтор (до 5); 400/401/403/413/редирект → `failed`. В журнале — только коды.

Чистка: выключенные подписки без строк очереди удаляются через 30 дней (`purge`).

### 2.6. Тексты push (закрытый список, PROCESS 11)

`digest_operator`, `digest_manager`, `alarm_callbacks_overdue`, `alarm_handoff_unaccepted`,
`alarm_grey_unassigned`, `client_transferred`, `staff_disabled`, `consultant_assigned`, `booking_consult_new`,
`handoff_new`, `handoff_assigned`, `task_assigned`, `grey_suggest`. Остальные виды — только колокол.
Тест: у каждого вида есть текст, подстановки — только числовые аргументы, строка из `params` в текст не
попадает.

### 2.7. Ключи VAPID

В `/etc/crm/app.env`, генерирует `crmctl install` (дописывает `crmctl update`, если нет) функцией
`generateVapidKeys()` (`src/server/platform/push/vapid.ts`). Приватный ключ не в репозитории и не в БД.
`VAPID_SUBJECT` — `mailto:` ящика сопровождения поставщика (вопрос владельцу, §4). Смена ключей делает
все подписки недействительными — после неё сотрудники включают уведомления заново.

## 4. Вопросы владельцу

1. **Включать ли push у ЦРП и когда.** Нужен письменный ответ ЦРП об использовании push-сервисов Apple и
   Google (в тексте нет ПДн, содержимое зашифровано, но сервисы видят факт и время доставки на
   устройство). Рекомендуем: после пилота (PLAN §6), после проверки на iPhone и Android.
2. **`VAPID_SUBJECT`.** Адрес связи для Apple и Google. Рекомендуем общий ящик сопровождения SalemAI
   (`mailto:`), а не личный и не ящик клиента.
