# Руководство по эксплуатации (RUNBOOK)

Нормативно: `docs/DEPLOY.md` §4–5, `docs/ARCHITECTURE.md` §8.3. Здесь — команды. Разделы ведут разные задачи, заголовки
второго уровня не пересекаются. Секретов, адресов и паролей в этом файле нет и быть не должно.

## Пакет релиза

Каталог после распаковки `crm-<клиент>-<версия>.tar.zst` (или сам архив: `crmctl` распакует его в
`/var/lib/crm/packages/<имя>`):

| Файл | Что |
|---|---|
| `manifest.json` | `customer`, `version`, `buildId`, `schemaVersion` (имя последней SQL-миграции), `configSchemaVersion`, `minFromVersion`, `images[]` (`ref` вида `crm-app:<версия>` и `digest` = `docker image inspect --format '{{.Id}}'`) |
| `manifest.sig` | подпись манифеста (проверка — O4c, пока заглушка) |
| `images.tar` | `docker save` образа `crm-app:<версия>` |
| `compose/` | `compose.yaml` и `postgres-init/` из `deploy/compose/` |
| `nginx/` | `crm.conf.template`, `maintenance.html` из `deploy/nginx/` |

## Установка с нуля

Порядок и роли — DEPLOY §4. Здесь шаги 2–3.

1. Root ЦРП, один раз (пакет уже распакован в `/root/crm-pkg`):
   ```
   ./install.sh --package /root/crm-pkg --domain crm.<сайт ЦРП> --owner-user crmops
   ```
   Ставит Docker, nginx, certbot, ufw (22, 80, 443), fail2ban, chrony, `crmctl` (node и `crmctl.mjs`
   берутся из образа пакета), cron `crmctl health` раз в 5 минут, logrotate на 14 дней, сеть `crm_ingest`,
   sudo для `crmops` **только** на `/usr/local/bin/crmctl`. БД и приложение не создаёт.
2. Владелец, от `crmops`:
   ```
   sudo crmctl install /root/crm-pkg --domain crm.<сайт ЦРП> --admin-phone <номер> --admin-name "<имя>"
   ```
   Шаги: проверка окружения и подписи, `/etc/crm/{app,db,project}.env` (0600), загрузка образов,
   БД, роли, миграции под `crm_owner`, `deploy/postgres/grants.sql`, `installId`, первый
   администратор, запуск `app` и `worker`, проверка `/api/health`. В `app.env` создаётся и
   `CRM_PROXY_SECRET`, его копия для nginx — `/etc/crm/nginx-proxy.d/secret.conf` (D-155). Печатать и
   хранить его вне сервера не нужно: при потере `crmctl update` выпустит новый.
3. **Вывод команды показывается один раз.** Сохраните вне сервера: `installId`, ссылку первого входа
   администратора (одноразовая, 72 ч, формат `https://<хост>/invite#<токен>`), три ключа
   (`CRM_SECRETS_KEY_k1`, `CRM_PHONE_HMAC_KEY`, `CRM_IIN_HMAC_KEY`). Копия ключей вне сервера и
   запечатанный конверт директору — обязательны: без ключей зашифрованные поля не восстановить.
4. Сертификат: `certbot certonly --webroot -w /var/www/certbot -d crm.<сайт ЦРП>`, затем
   `./install.sh --nginx-only --domain crm.<сайт ЦРП>` (подставит шаблон и перечитает nginx).
5. Лицензия: `installId` → владельцу → подпись офлайн → `crmctl license install` (команда P10).
   До этого установка в состоянии `missing` («только чтение»).

Если установка оборвалась (например, `app` не ответил), повторный `crmctl install` безопасен: файлы
окружения и `installId` сохраняются, миграции идемпотентны, выдаётся новая ссылка входа.
`state.json` пишется только после успешного `/api/health`; пока его нет, `install` не отказывает.

## Обновление

```
sudo crmctl update /var/lib/crm/packages/crm-crp-1.2.0.tar.zst
```

1. Пакет: версия выше текущей, тот же клиент, `minFromVersion`, схема не ниже накатанной, подпись.
2. `docker load`, сверка образов с манифестом; **лицензия проверяется новым образом**, `invalid` —
   стоп, прежняя версия работает.
3. Если есть ненакатанные миграции — копия БД (`/usr/local/lib/crm/backup.sh`, ставит O3); не вышла —
   стоп. Затем `migrate` под `crm_owner` и `grants.sql` (применяется при каждом обновлении).
   Окружение (D-155): если в `/etc/crm/app.env` нет `CRM_PROXY_SECRET`, строка дописывается в конец
   файла, прежние строки не меняются. Секрет для nginx пишется в `/etc/crm/nginx-proxy.d/secret.conf`.
   В конфиг nginx на хосте (`/etc/nginx/conf.d/crm.conf`, другой путь — `CRM_NGINX_CONF`) в каждый
   location с `X-Via-Proxy` дописывается `include /etc/crm/nginx-proxy.d/*.conf;`, если его там нет.
   Затем `nginx -t` и `systemctl reload nginx`. Каждое изменение видно в выводе команды, значение
   секрета не печатается. Если `nginx -t` не прошёл, конфиг возвращается как был, и обновление
   останавливается: прежняя версия работает.
4. Новая версия поднимается отдельным контейнером `crm-app-next` в сети `crm_internal` (порты не
   публикуются) и проверяется `/api/health`; нездорова — стоп, прежняя работает.
5. Переключение: `docker compose up -d app worker` с новой версией (app пересоздаётся за секунды,
   nginx показывает страницу обслуживания). Проверка `/api/health` сразу и через 2 минуты
   (`--recheck-seconds`). Сбой любой из них или `compose up` — **автооткат** на прежний тег.
6. Код выхода: 0 — готово; 1 — остановлено или откатилось, прежняя версия работает; 2 — откат не
   удался, нужно вмешательство (`crmctl status`, `docker compose -p crm logs app`).

Окна выкладки в пилот — DEPLOY §5.3.

Если приложение не стартует и в `docker compose -p crm logs app` есть «Запуск остановлен, окружение
/etc/crm/app.env не годится», значит в production нет `CRM_PROXY_SECRET` или `APP_ORIGIN`
(docs/CONFIG.md §7). Секрет дописывает `sudo crmctl update` при обновлении на новый пакет. Если строку
удалили вручную, а нового пакета нет, верните её в `/etc/crm/app.env`: `CRM_PROXY_SECRET=<значение>`, где
значение — строка в кавычках из `/etc/crm/nginx-proxy.d/secret.conf`. Затем выполните
`docker compose -p crm -f /var/lib/crm/compose/compose.yaml --env-file /etc/crm/project.env up -d app`.
`APP_ORIGIN` вписывается вручную: `APP_ORIGIN=https://<хост>`.
Если в журнале раз в час появляется `[security] ВНИМАНИЕ: запрос с меткой прокси … без верного
секрета`, значит nginx не передаёт секрет. Проверьте, что в
`/etc/nginx/conf.d/crm.conf` есть `include /etc/crm/nginx-proxy.d/*.conf;`, затем выполните `nginx -t` и
`systemctl reload nginx`.

## Откат

```
sudo crmctl rollback
```

Поднимает прежнюю версию (около минуты), возвращает её `compose.yaml`, меняет местами `current` и
`previous`: повторный `rollback` вернёт новую. БД не откатывается (миграции только добавляющие,
D-060); правки настроек, сделанные новой версией, после отката не видны, команда об этом
предупреждает. Образ прежней версии должен быть на сервере (чистка образов оставляет текущий и
прежний). Выход 2 — прежняя версия не отвечает. Выход 1 с «Откат на … невозможен» — ядро прежнего образа
собрано для другого клиента, общее или без времени сборки (до D-290): такой образ клиенту не ставится
(D-307), нужен пакет актуальной сборки через `crmctl update`.

## Состояние и проверка

```
sudo crmctl status   # версии, installId, контейнеры, /api/health
crmctl health        # одна строка и код выхода 0/1 (для cron и мониторинга)
```

Файлы: `/var/lib/crm/state.json` (версии, без секретов), `/etc/crm/project.env` (`CRM_VERSION` для
compose), `/var/lib/crm/compose/` (текущий compose), `compose.prev/` (прежний). Переменные для тестов
и нестандартных путей: `CRM_ETC_DIR`, `CRM_LIB_DIR`, `CRM_CLI_DIR`, `CRM_BACKUP_CMD`.

## Лицензия

Файл `CRM1.<payload>.<подпись>` (Ed25519), выдаётся владельцем под `installId` установки
(`scripts/license-sign.ts`, DEPLOY §8.2). Ключи проверки — открытые половины, вшиты в ядро образа при
сборке (`build.mjs --license-keys`); закрытых ключей на сервере нет и быть не должно.

```
sudo crmctl status                       # installId — его нужно владельцу для выпуска лицензии
sudo crmctl license install <файл>       # проверить ядром ТЕКУЩЕГО образа и положить на место
sudo crmctl license status               # что в файле, что о нём думает образ, что записано в license_state
```

- Где лежит: `/var/lib/crm/license/license.crm` (прежняя — `license.crm.prev`). Том в приложении и
  воркере только для чтения; применяют файл в течение минуты, воркер пересчитывает состояние раз в час.
- `install` отказывает, если подпись не сходится, лицензия выдана другому клиенту или на другой
  `installId`, срок не начался или уже вышел вместе с льготой, образ собран не для этого клиента.
  Файл при отказе не меняется. Загрузка — мутация безопасности (D-054), работает и в «только чтение».
- `crmctl update` проверяет лицензию НОВЫМ образом до переключения: не сходится — обновление не идёт.
  Нет файла — не помеха (состояние `missing`). Лицензия прежней сборки (`wrong_build`) — не помеха, пока
  не прошло 7 суток от сборки нового образа: команда печатает «Внимание: … работает в льготе до …».
- **После обновления сборки** лицензия под прежнюю сборку работает в льготе только до «время сборки нового
  образа + 7 суток» (не от момента обновления; D-290). В этот срок: `sudo crmctl status` → версия и
  `installId` владельцу → владелец выпускает лицензию под новую сборку (или без `buildId`) →
  `sudo crmctl license install <файл>`. `crmctl license status` показывает сборку образа, время сборки и
  «льгота до». Пакет, пролежавший больше 7 суток от сборки, с лицензией под сборку не обновится — нужна
  лицензия без `buildId` или свежая сборка.
- `crmctl install` до БД спрашивает ядро образа о водяном знаке: общий образ (без клиента) или образ
  другого клиента не ставится — нужен пакет, собранный для этого клиента (D-213).
- **Образы без времени сборки клиентам не выдаются** (D-307): ядро, собранное до D-290, не сообщает
  `builtAt`, и `crmctl install`, `update` и `rollback` на такой образ отказывают («без времени сборки»).
  Сборка после D-290 сообщает время сборки всегда (`BUILT_AT`, пусто — момент сборки, ниже).
- Состояние в `license_state` каждый раз считается заново из подписанного текста. Правка строки
  (`state`, `invalid_since`, `last_seen_at`) «только чтение» не снимает и льготу не продлевает: льгота есть
  только у лицензии прежней сборки, до времени сборки + 7 суток и не дольше срока подписанной копии в БД
  (D-290). Битый, подменённый или нечитаемый (каталог, нет прав) файл при рабочей копии в БД не мешает:
  работа идёт по копии, в журнале приложения `license_file_rejected` (`reason: unreadable` и код ошибки — файл
  не читается) — замените файл (`license install`).
- Ключи клиентского образа: `docker build --build-arg CUSTOMER_ID=<клиент> --build-arg BUILD_ID=<id>
  --build-arg BUILT_AT=$(date +%s%3N) --secret id=license_keys,src=<keys.json> .`. `BUILT_AT` — время сборки
  (epoch-мс) в водяном знаке; пусто — момент сборки слоя. `keys.json` — `{ "<kid>": "<base64 32 байта>" }`, только
  открытые ключи; без него сборка с `CUSTOMER_ID` падает. Ключи `test-*` в такой сборке запрещены.

**Если сервер в `read_only` (или `invalid` / `missing`):** просмотр, вход и полная выгрузка работают,
правки возвращают 423, раздача и рассылки стоят, приём лидов отвечает «не принимаем». Данные целы.
1. `sudo crmctl license status` — причина: срок и льгота вышли (`expired`), подпись не сходится
   (`bad_signature`, `unknown_kid`), чужая установка (`wrong_install`), чужой клиент, файла нет, часы
   сервера позади дольше 48 ч (`clock`).
2. Срок вышел: запросить у владельца новую лицензию на тот же `installId` и поставить
   `sudo crmctl license install <файл>`. Через минуту `crmctl license status` покажет `valid`.
3. `wrong_install`/`wrong_build`: лицензия выпущена не под эту установку или сборку — владельцу нужен
   `installId` и версия из `crmctl status`; после обновления лицензия под новую сборку должна встать до
   «льгота до» из `crmctl license status`. `unknown_kid`: образ собран без ключа этой подписи — нужен образ
   с актуальным набором ключей, а не новый файл.
4. Часы сервера позади (тревога «часы позади», в журнале `license.clock_jump` с `backward`; через 48 ч —
   `read_only`, причина `clock`): исправить время (`chrony`, `timedatectl`), проверить `date -u`. Как только часы
   снова не позади времени лицензии больше 10 минут, эпизод кончается сам, и через минуту `license status` покажет
   прежнее состояние (D-314). Пока часы позади, время лицензии стоит; один перевод назад продлевает срок до 48 ч,
   потом «только чтение». Часы, которые раз в 48 ч возвращают к времени лицензии, держат срок сколько угодно —
   это остаток без доверенного времени (D-314 (а)), признак — тревоги «часы позади» почти каждые двое суток при
   неизменном времени лицензии в `license-clock status`; сообщить владельцу. Перезапуски ничего не копят и не мешают. `crmctl license-clock status` покажет
   время лицензии, часы сервера и длительность эпизода.
5. Часы сервера спешили и их исправили (тревога «часы» `forward`, затем «часы позади»): время лицензии стоит, пока
   верные часы его не догонят, — столько, на сколько спешили часы. Спешили до 48 ч — блокировки нет, ничего не
   делать. Больше (время лицензии успело уйти вперёд больше чем на 48 ч) — через 48 ч эпизода будет «только чтение»
   до догона; снять сразу: `sudo crmctl license-clock reset --yes` (только когда часы уже верные: время лицензии
   ставится на показание часов; команда пишет `license.clock_reset` в журнал аудита и пересчитывает состояние).
   psql для этого не нужен. Сброс — откат времени лицензии: делается только после починки часов, каждый попадает в
   аудит (D-212, D-314).
6. Не помогло — `crmctl job run license` пересчитывает состояние сразу. Причина `error` в `license status` или
   `license_refresh_failed` в журнале приложения — пересчёт не удался (БД недоступна, нет прав на `license_state`):
   работа идёт в «только чтении», выгрузка и мутации безопасности доступны (D-314); чинить БД, затем `job run license`.

**Если `app` или `worker` не стартует и в журнале `license.runtime_tamper`** (D-312, D-314,
`sudo docker compose -p crm -f /var/lib/crm/compose/compose.yaml --env-file /etc/crm/project.env logs app`):
в команде или `NODE_OPTIONS` контейнера (compose или `/etc/crm/app.env`) есть явная подгрузка кода или отладка —
`--require`/`-r`, `--import`, `--loader`, `--inspect`, `--debug` — или в окружении `LD_PRELOAD`/`LD_AUDIT` (тревога
называет, что именно). Вернуть `/var/lib/crm/compose/compose.yaml` из пакета этой версии (`deploy/compose/`), убрать
лишнее из `app.env` и поднять контейнеры заново (`up -d`). Отладчик, APM-агенты и прочие `--require` на бою не
включаются — разбор идёт на стенде на общей сборке.

**Если в журнале `license.runtime_signal`** (запуск идёт): процесс запущен не как в поставке — обёртка вместо
`node --disable-sigusr1 server.js` (worker — `dist/worker.mjs`), другие флаги node, переменные `LD_LIBRARY_PATH`,
`OPENSSL_*`, `NODE_PATH`, `GCONV_PATH`, `NODE_COMPILE_CACHE`, каталоги `$HOME/.node_modules`, `$HOME/.node_libraries`,
`<prefix>/lib/node`. Тот же признак — запись `license.runtime_signal` в аудите. Вернуть команду и окружение из пакета,
как выше. Проверка запуска — планка, а не защита от root: нагрузка, написанная под неё, её обходит — это правка
выполняемого кода и нарушение договора (ARCHITECTURE §8.4).

## Копии и восстановление

Нормативно: DEPLOY §6, D-031, D-044. Команды: `crmctl backup …` и `crmctl restore …` (исходники —
`scripts/crmctl/backup.ts`, `restore.ts`, общее — `backup-lib.ts`). Файлы развёртывания — `deploy/backup/`.

### Что делает копия

`crmctl backup run --kind hourly|daily|weekly [--verify|--no-verify]`:

1. Открывает транзакцию со снимком, снимает `pg_dump -Fc` этим снимком и в нём же считает таблицы,
   последнюю миграцию и строки ключевых таблиц (`users`, `clients`, `contacts`, `cards`, `calls`, `events`,
   `deals`, `audit_log`, `license_state` и др.).
2. Проверка восстановления до шифрования (по умолчанию для `weekly`): дамп разворачивается во временную БД
   `crm_restorecheck*`, счётчики сверяются со снимком, БД удаляется. Ключ хранителя не нужен.
3. `age -R` на публичные ключи двух хранителей. Файл получателей с одним ключом отвергается. Открытый дамп
   живёт только во временной папке тома и удаляется всегда.
4. Рядом пишутся `<имя>.sha256` и `<имя>.counts.json` (только числа строк, без данных).
5. Ротация на локальном томе: часовых 12, дневных 7, недельных 4 (`BACKUP_KEEP_*`). Чужие файлы не трогаются.
6. Второй сервер: только если `BACKUP_OFFSITE_TARGET` задан и `BACKUP_OFFSITE_DC_CONFIRMED_KZ=1`
   (письменное подтверждение провайдера, что ЦОД в РК, D-044). Иначе копии остаются только на томе,
   в статусе `offsite = disabled_unconfirmed`. Сбой отправки не отменяет локальную копию: статус `failed`.
7. Статус `BACKUP_STATUS_FILE` (JSON): `ok`, `at`, `kind`, `file`, `sizeBytes`, `verified {at, ok, ms}`,
   `offsite {state, lastSentAt}`, `error` (без паролей). Его читает healthcheck (`backup`, `backup_offsite`).

Имя файла: `crm-<вид>-<ГГГГММДД>T<ЧЧММСС>Z.dump.age` (UTC).

### Установка на боевом сервере

1. `deploy/backup/install-age.sh` (нужен `age`; из пакета ОС, иначе официальный релиз с проверкой суммы).
2. `/etc/crm/backup.env` по образцу `deploy/backup/backup.env.example` (root, 0600); `BACKUP_OFFSITE_DC_CONFIRMED_KZ=0`.
3. `/etc/crm/backup-recipients.txt` по образцу `backup-recipients.example`: публичные ключи владельца и директора
   (`age-keygen -y ключ.txt`). Закрытых ключей на сервере нет.
4. Задания — `deploy/backup/crontab.example` → `/etc/cron.d/crm-backup`. В пилот часовые 09:00–19:00, ночью 02:00.
5. Второй сервер: на нём раз в сутки `deploy/backup/offsite-prune.sh <каталог>` (запись с боевого сервера не
   стирает, поэтому чистка локальная): остаётся последняя часовая и ночные не старше 35 дней.

Ключи окружения (HMAC, AES, VAPID) в копию не входят (DEPLOY §6.1).

### Проверка восстановления

- `crmctl restore verify --file F.dump.age --identity КЛЮЧ [--report out.json]` — сумма, расшифровка ключом
  хранителя, восстановление во временную БД, сверка с `F.counts.json`, удаление БД. Код выхода 0 только если
  всё сошлось и уложились в 30 минут.
- `crmctl restore apply --file F.dump.age --identity КЛЮЧ --db ИМЯ [--no-acl]` — восстановление в НОВУЮ БД
  (существующую не трогает, при ошибке недовосстановленную удаляет). После — `deploy/postgres/grants.sql` и
  `crmctl update`. Ключ хранителя передаётся путём к файлу и нигде не сохраняется.
- Отчёт содержит время этапов: `checksumMs`, `decryptMs`, `restoreMs`, `countMs`, `totalMs`. Цель — не дольше
  30 минут (DEPLOY §6.3). Время каждого учебного восстановления записывается в журнал учений у владельца.

Восстановление с реальными данными на стенде и ИИ-агентом не делается (DEPLOY §6.3).

### Учебное восстановление в CI

`.github/workflows/restore-drill.yml` раз в сутки (02:30 Алматы) и вручную: тесты копий и
`deploy/backup/drill.sh` — миграции → синтетика (`seed-synthetic.sql`) → копия с проверкой → восстановление
ключом каждого из двух учебных хранителей. Время восстановления попадает в сводку прогона и в артефакт
`restore-drill-report` (`restore-keeper1.json`, `restore-keeper2.json`, `summary.md`). Падение прогона — сигнал
владельцу репозитория. Локально: `ADMIN_DATABASE_URL=… deploy/backup/drill.sh [каталог отчёта]`.

### Если копия не прошла

| Признак | Что делать |
|---|---|
| `status.ok = false` | Прочесть `error` в статусе. Типичные причины: файл получателей, место на томе, БД недоступна |
| `Проверка восстановления не прошла` | Копия не шифруется и не сохраняется. Сообщить разработчику, ничего не удалять |
| `offsite = failed` или `disabled_unconfirmed` | Первое: проверить ключ и сеть до второго сервера. Второе: ожидаемо, пока нет подтверждения ЦОД в РК |
| Не совпала контрольная сумма | Копия повреждена, брать предыдущую |

## Учебный стенд и демо-данные

Синтетический сид для учебного стенда и e2e (PLAN O8b). Код — `scripts/seed/`, команда — `scripts/crmctl/seed.ts`.
Реальных людей и компаний в данных нет: названия составлены из слов и порядкового номера, номера клиентов только
`+7 709 …`, служебные номера сотрудников — `+7 709 100 00 NN`. **На боевой установке не запускать.**

```
crmctl seed [--seed <зерно>] [--clients 500] [--operators 5] [--layers a,b,…] [--i-know-this-is-a-stand]
# из исходников: npx tsx scripts/crmctl/seed.ts …
```

Нужны накатанные миграции и `DATABASE_URL` (как у остальных команд). Что происходит по порядку:

1. Применяется пресет тем же путём, что `crmctl config apply --yes` (слои `base`, `kz`, `consulting-sales` и накладка
   `clients/crp` из каталога пресетов; `--layers` заменяет список). Том ассетов — `CRM_ASSETS_DIR`, без него —
   временный каталог. Пресет уже записан и не менялся — «без изменений».
2. Заводятся сотрудники: администратор, РОП, дежурный (вторая учётка с ролью РОП), 5 операторов, 2 консультанта с
   направлениями и недельным графиком (у второго ближайшая пятница выходная), директор, глава маркетинга
   (руководитель команды `marketing`).
3. Серия БР по четвергам берётся из пресета; мероприятия на горизонт создаёт тот же `events-ensure`, что и воркер.
   Добавляются четыре прошедших четверга (для явки и неявки). Дежурный ставится на два ближайших БР.
4. 500 клиентов (по умолчанию) с контактами, номерами и карточками: 140 новых у операторов, 60 в пуле, 90 недозвонов,
   70 перезвонов (часть на сегодня и на завтра), 40 «Договорились» (записи на БР и консультантов, «серые» записи,
   задачи), 10 клиентов с покупкой, закрытые и списанные. История звонков согласована с карточкой. К этому
   добавлены сделки, передачи в отдел, задачи, заметки и стоп-лист.

**Повторный запуск ничего не меняет**: id строятся из зерна, вставки идут `ON CONFLICT DO NOTHING`, отчёт показывает
«без изменений». Другое `--seed` даёт другой набор рядом с прежним. «Сегодня» берётся из часов сервера, поэтому
перезвоны и записи привязаны к дню первого запуска; для свежих дат разверните стенд заново (удалять строки сид не
умеет — БД стенда пересоздаётся).

**Пароли.** Сид создаёт учётки без пароля в репозитории. Без `CRM_SEED_PASSWORD` каждому создаваемому сотруднику
генерируется свой пароль и **печатается один раз** в конце вывода; в базе остаётся только хеш. Со своим
`CRM_SEED_PASSWORD` (проходит ту же политику, что обычный пароль) он общий для всех учёток и не печатается. Вход —
по номеру телефона.

**Защита (три замка).** В образе всегда `NODE_ENV=production`, поэтому одного флага мало:
1. `--i-know-this-is-a-stand`;
2. `CRM_STAND=1` в окружении стенда (на боевой установке этой переменной нет и быть не должно) — без неё сид отказывает до открытия базы;
3. проверка самой базы: сид отказывает, если есть клиенты с номерами вне блока `7709`, если настройки менялись не пресетом
   (источники ui/cli/rollback/migration) либо уже применены, а в базе есть сотрудники вне блока `7709` (применял не сид).

Для стенда в production-режиме задайте также `CRM_PHONE_HMAC_KEY` (иначе стоп-лист не построить: ключ обязателен).

## Известные ограничения

- Проверка лицензии при `update` настоящая (P10, ядро нового образа). Проверка подписи пакета — заглушка
  (реализует O4c): без `CRM_VERIFY_STUB=allow` `install` и `update` останавливаются. Разрешение допустимо
  только на стенде и в тестах.
- Переключение — пересоздание `app` (секунды простоя, страница обслуживания), не бесшовная замена:
  два `app` с публикацией порта и псевдонимом `crm-app` одновременно не живут. Новая версия до
  этого проверяется отдельным контейнером.
- Живость `worker` проверяет `node dist/worker.mjs --health`: свежий файл пульса (healthcheck в compose).
  Ручной запуск фоновых задач и просмотр журнала: `crmctl job list`, `crmctl job run <имя> [--space <ключ>]`;
  прогон идёт под той же блокировкой, что у воркера, параллельный запуск пропускается.
