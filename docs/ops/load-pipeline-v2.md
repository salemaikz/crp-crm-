# Нагрузочный прогон доски оператора (линия C5, воронка v2)

Нужен линии F2 (индексы, `docs/pipeline-v2-design.md` §7.2). Скрипт: `tests/load/board.ts` (не входит в unit и
integration). Запуск: `TEST_DATABASE_URL=postgres://…/<отдельная БД> FEATURE_OP_BOARD=1 FEATURE_CALLBACK_V2=1 node --import tsx --test tests/load/board.ts`;
схему и данные прогон создаёт и удаляет сам, `LOAD_KEEP=1` оставляет схему для разбора планов. Только синтетика:
номера `+7 709 …`, компании выдуманные.

## Данные и среда

300 200 карточек (200 мира изоляции + 300 000), 20 операторов по 15 000, один РОП. Состояния: 30 % «Новая», 25 %
«Недозвон», 20 % «Перезвон», 5 % «Договорились» (открытая сделка и запись: 60 % БР группой, 40 % консультация), 5 %
клиенты, 15 % закрытые (закрыты за последние 60 дней). Из карточек перезвона 30 % — «огонёк» (просрочены или на
сегодня). Каждые 7-й — с добавкой горячести. Один номер на клиента, 20 % стационарных.

4 vCPU, 16 ГБ ОЗУ, Postgres 16.15 на той же машине (`shared_buffers` 128 МБ, `work_mem` 4 МБ, `jit=on`),
приложение (тестовый процесс) на ней же. Размер `cards` с индексами — 151 МБ. Раундов: 3 на оператора. Цифры с
боевого сервера будут близкими, но не равными (сеть не учтена).

## Результаты

Критерий C5: p95 ответа колонки ≤ 300 мс. Миллисекунды; «до F2» — только индексы схемы v1, «набор §7.2» — индексы
дизайна §7.2 (создаются в самом прогоне). Значения p95 / максимум по запросам; 3 прогона скрипта дали тот же порядок.

Критерий выполнен уже на индексах схемы v1: p95 колонки 125 мс, максимум 223 мс. Разброс между прогонами 20–40 %
(повтор на индексах v1 в том же запуске дал итого p95 135 мс), поэтому разницу между столбцами меньше этого не
читаем как выигрыш.

Что стоит учесть:
- Доска целиком при одновременном открытии 20 операторами — 450–560 мс p95. Это не медленный запрос, а процессор:
  20 × 12 запросов на 4 ядрах вместе с самим процессом прогона. Одна колонка у 20 операторов одновременно — 144–181 мс.
- Самые тяжёлые запросы — РОП, «Бизнес-разбор» и «Консультация» (сортировка всех «Договорились» пространства по дате
  записи, 15 000 строк), 120–220 мс. Растёт линейно с числом «Договорились».
- Поиск РОП по очень общему запросу («нагрузка 5» — совпадает половина базы) около 300 мс: триграммный индекс
  читает все совпадения, затем сортировка по давности. Узкие запросы — 10–100 мс. У оператора поиск идёт по своим.

## Что показал разбор планов (`EXPLAIN`)

1. **Индексы дизайна `cards_heat_owner_idx` и `cards_heat_space_idx` (с `state` в начале) не используются** — 0 вызовов
   `idx_scan` за прогон. Колонка «Перезвон» берёт два состояния сразу (`retry`, `callback`), и порядок `heat DESC`
   по такому индексу не получается. Рабочие индексы — **без `state` в ключе**, частичные:
   ```sql
   CREATE INDEX cards_cb_owner_idx ON cards (space_id, owner_user_id, heat DESC, next_call_at, id)
     WHERE state IN ('retry','callback') AND hold_reason = '';
   CREATE INDEX cards_cb_space_idx ON cards (space_id, heat DESC, next_call_at, id)
     WHERE state IN ('retry','callback') AND hold_reason = '';
   ```
   Замер на 300 тыс.: часть «не огонёк» колонки «Перезвон» у РОП — 53 мс (параллельный seq scan) → **0,3 мс**;
   у оператора 1,6 мс (по индексу пространства) → **0,2 мс** (по индексу владельца).
2. `cards_fire_owner_idx` (срок для «огонька») использован 585 раз — нужен. `cards_fire_space_idx` — 28 раз, вклад мал
   (огоньков у пространства десятки тысяч, сортировка в памяти идёт быстро); можно не создавать.
3. `cards_closed_idx` (закрытые за `recentDays`) использован 191 раз, колонка «Мусор» у РОП 49 → 34 мс — нужен.
4. `cards_client_return_idx` — 10 раз, вклад не измерен (возврат клиента после покупки, № 34); оставить по решению F2.
5. `bookings_deal_idx (deal_id, starts_at)` вместо `(deal_id)` использован 573 тыс. раз (запись открытой сделки), но
   разницы со схемой v1 нет: запись на сделку одна-две. Менять не обязательно.
6. Охват «своё или временный» (`owner = я OR acting = я`) идёт через `cards_acting_idx` и `cards_queue_idx` (BitmapOr):
   отдельный индекс не нужен.
7. «Новые» (оператор 20–30 мс, РОП 60 мс на 90 000 «Новых») индекса не требуют. Если число «Новых» вырастет,
   вариант — `(space_id, owner_user_id, heat DESC, assigned_at, id) WHERE state = 'new' AND hold_reason = ''` (не замерен).

**Предложение для F2:** `cards_fire_owner_idx`, `cards_cb_owner_idx`, `cards_cb_space_idx`, `cards_closed_idx`; остальные из
набора §7.2 не создавать без нового замера. Критерий C5 они не требуют (выполнен и без них), а выигрыш дают на росте
базы выше 300 тыс. и у РОП.

## Отступления от дизайна, найденные прогоном

- **«Новые» с мобильными раньше** считается по номерам клиента каждой строки охвата. У оператора (свои, до 5 000) это
  20–30 мс, у РОП на 90 000 «Новых» — 630 мс на страницу. Поэтому признак «мобильный» действует только при охвате
  `own`; у РОП и директора «Новые» идут по горячести и дате выдачи. Решение зафиксировано в коде (`boardRepo.ts`).
- Сортировки доски «по сроку», «по дате выдачи», «по названию» (дизайн §9.4) сервером не делаются: колонки «Новые» и
  «Перезвон» идут только по горячести. Интерфейсу, если он их оставит, нужно ограничение 200 карточек в колонке с
  подсказкой «уточните поиск» (решение §9.4, второй вариант).
