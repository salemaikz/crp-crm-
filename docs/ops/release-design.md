# Релизный пакет и подпись (O4c, O-pkg)

Дизайн architect для O4c и O-pkg. Решение — D-315 (предложено, уточняет D-064 и D-027). Нормативно, когда
решение принято: DEPLOY §5, ARCHITECTURE §8.2–8.3. RUNBOOK описывает команды и правится под код.
Секретов, адресов и закрытых ключей в этом файле нет и быть не должно.

## 1. Что защищает подпись и чего не защищает

Защищает:
- от подмены или порчи пакета по дороге и на диске сервера (любой байт любого файла);
- от пакета, который собрали CI или ИИ-сессия без одобрения владельца: боевой `crmctl` доверяет только
  ключам релизов, а закрытый ключ релизов есть только у владельца (D-064);
- от пакета, подписанного ключом стенда (`stage-*`): на бою ключ стенда не признаётся;
- от пакета для другого клиента и от понижения версии через `update`: клиент и версия входят в подпись.

Не защищает:
- от root сервера клиента: он может заменить сам `crmctl`. Это честная граница DEPLOY §8.3, а не цель O4c;
- от CI, который подменил код до сборки артефакта, одобренного владельцем. Защиту дают защищённые теги,
  Environment с одобрением и сводка ключей при подписи (§5.3). Воспроизводимой сборки и provenance нет (В-5).

## 2. Пакет `crm-<клиент>-<версия>.tar.zst`

### 2.1. Состав

| Путь в архиве | Что |
|---|---|
| `manifest.json` | **первый** член архива, не больше 256 КиБ; подписывается целиком (§3) |
| `images.tar` | `docker save crm-app:<версия>` — один образ: приложение, воркер, `migrate` и `crmctl` |
| `compose/` | `compose.yaml`, `postgres-init/` из `deploy/compose/` |
| `nginx/` | `crm.conf.template`, `maintenance.html` из `deploy/nginx/` |
| `migrations/` | копия `migrations/*.sql` из образа: для просмотра владельцем при подписи. Накатываются файлы из образа; сборка пакета сверяет, что копии совпадают побайтно |
| `install.sh` | из `deploy/install.sh` |

Подпись в архив не входит. Это отдельный файл рядом с архивом: `crm-<клиент>-<версия>.manifest.sig`
(стенд: `crm-<клиент>-<версия>.stage.sig`). После проверки `crmctl` кладёт подпись в распакованный каталог
как `manifest.sig`. В каталоге пакета, распакованном вручную, подпись тоже лежит как `manifest.sig`.

Приложение и воркер — **один образ** с разными командами (`server.js`, `dist/worker.mjs`), как в compose.
В образе ядро обфусцировано и несёт водяной знак клиента (`CUSTOMER_ID`, `BUILD_ID`, `BUILT_AT`, D-028, D-213).
Нет `src/`, `*.ts`, `*.map`, `tests/`, `.git`, `.env*` и ключей. Это проверяет `scripts/check-image.sh` на образе,
а сборщик пакета не берёт такие пути в архив.

### 2.2. Формат архива

- POSIX ustar, сжатый zstd. Члены архива — только обычные файлы (тип `0`) и каталоги (`5`). Нет ссылок,
  устройств, pax- и GNU-заголовков. Пути относительные, ASCII `[A-Za-z0-9._/-]`, не длиннее 100 символов,
  без `..`, без `/` в начале и без повторов. Размер одного файла — до 8 ГиБ (предел ustar).
- Сборка воспроизводимая: члены идут по имени, `mtime = builtAt`, владелец 0:0, права 0644/0755.
- Архив пишет и читает свой модуль на `node:zlib` (zstd есть в Node ≥ 22.15, в образе `node:22-slim` он есть;
  сборка проверяет версию). Системные `tar` и `zstd` не нужны ни на сервере, ни у владельца, а ссылки и
  обход пути исключены самим читателем, а не флагами `tar`.

### 2.3. `manifest.json` (формат 2)

```json
{
  "format": 2,
  "customer": "<клиент>",
  "version": "0.9.0",
  "buildId": "<id>",
  "builtAt": 1761000000000,
  "commit": "<40 hex>",
  "schemaVersion": "2026-10-2X-<поток>-<slug>.sql",
  "configSchemaVersion": 3,
  "minFromVersion": "",
  "images": [{ "ref": "crm-app:0.9.0", "digest": "sha256:<64 hex>" }],
  "releaseKeys": [{ "kid": "rel-2026a", "sha256": "<64 hex>" }, { "kid": "rel-2026b", "sha256": "<64 hex>" }],
  "files": [{ "path": "images.tar", "sha256": "<64 hex>", "size": 123 }]
}
```

- `files` — все члены архива, кроме `manifest.json` и каталогов. Набор в архиве должен **совпадать** с ним:
  если файл лишний, отсутствует или у него другой размер или sha256, пакет отвергается.
- `releaseKeys` — каким ключам релизов будет доверять `crmctl` этой версии (`kid` и sha256 сырого открытого
  ключа, 32 байта). Владелец видит этот список при подписи (§5.3), а `update` сверяет его с самим `crmctl` образа (§4.2).
- `builtAt` совпадает с `BUILT_AT` водяного знака: `update` и `install` сверяют это через ядро образа.
- Схема Zod строгая, неизвестные поля запрещены. Формат 1 (без `files`, `builtAt`, `commit`, `releaseKeys`)
  новый `crmctl` не принимает.

## 3. Подпись

- Алгоритм — Ed25519 через `node:crypto`, как у лицензии. Внешних утилит нет.
- Подписываются байты `"crm-release-v1\n"` и следом точные байты `manifest.json`. Канонизации JSON нет:
  проверяются ровно те байты, что лежат в архиве. Префикс отделяет подпись релиза от подписей другого назначения.
- Файл подписи — одна строка JSON: `{"format":1,"kid":"rel-2026a","sig":"<base64, 64 байта>"}`.
- Классы ключей по `kid`:

| Префикс | Кто держит закрытый | Кто доверяет |
|---|---|---|
| `rel-*` | только владелец, офлайн | `crmctl` любой сборки, если ключ вшит при сборке (`__CRM_RELEASE_KEYS__`) |
| `stage-*` | секрет GitHub Environment `stage` | только стенд: `/etc/crm/stage-keys.json` читается, если в `/etc/crm/app.env` есть `CRM_STAND=1`; из этого файла берутся только `stage-*` |
| `test-*` | никто: пара создаётся в тесте на лету | только тесты, ключи передаются через `Deps` |

- Открытые ключи релизов вшиваются в **хостовый `crmctl`** при сборке (`build-cli.mjs --release-keys <файл>`,
  BuildKit-секрет `release_keys`, JSON `kid → base64`), по образцу `license_keys`. Сборка с `CUSTOMER_ID`
  без ключей релизов, с `stage-*` или с `test-*` падает. Проверка подписи живёт в `crmctl`, а не в ядре
  нового образа: новому образу ещё нельзя доверять, поэтому проверять самого себя он не может.
- Резервный ключ `rel-2026b` вшивается сразу, а закрытая половина хранится отдельно. Если основной ключ
  потерян, следующий релиз подписывается резервным без перевыпуска `crmctl`. Отзыв ключа: следующий релиз
  выходит без него в `releaseKeys`, и после `update` хостовый `crmctl` его больше не принимает.

## 4. `crmctl`: порядок проверок

### 4.1. Проверка до любых действий (`install`, `update`, `package verify`)

1. Найти подпись: `--sig <файл>`, иначе `<архив без .tar.zst>.manifest.sig` рядом с архивом, а на стенде
   ещё `.stage.sig`. Для каталога пакета — `manifest.sig` внутри.
2. Прочитать первый член архива: это должен быть `manifest.json` не больше 256 КиБ. Проверить подпись
   ключом с этим `kid` из доверенного набора. Если `kid` неизвестен или подпись не сходится, это стоп.
3. Разобрать манифест строгой схемой. `update` дополнительно проверяет: тот же клиент, что в `state.json`;
   версия выше текущей; `minFromVersion`; схема БД не ниже текущей. `install` проверяет клиента по
   вшитому в `crmctl` `CUSTOMER_ID`, если он есть.
4. Потоком распаковать остальные члены в `/var/lib/crm/packages/.incoming-<uuid>/` и по пути посчитать
   sha256 и размер. Член вне `files`, повтор или тип не «файл/каталог» — стоп. В конце набор файлов должен
   совпасть с манифестом.
5. Записать `manifest.sig` в каталог и атомарно переименовать его в `packages/<клиент>-<версия>/`.
   Существующий каталог заменяется только тогда, когда его `manifest.json` побайтно совпадает с новым.
6. При любом отказе временный каталог удаляется. До конца шага 5 **ни одного** вызова `docker`, записи в
   `/etc/crm`, `compose/` и `state.json`.

Каталог, распакованный вручную, проверяется так же: подпись над `dir/manifest.json`, обход через `lstat`
(симлинк — стоп), совпадение набора файлов и sha256.

### 4.2. После загрузки образа и до переключения (`update` [2/7], `install` [4/8])

- Id образа совпадает с `images[].digest` (так уже работает сейчас).
- Водяной знак ядра образа: клиент и `builtAt` совпадают с манифестом (расширение `assertImageForCustomer`).
- `docker run --rm --network none crm-app:<v> node dist/crmctl.mjs keys --json` возвращает тот же набор,
  что `manifest.releaseKeys`. Иначе стоп: `syncCli` не может поставить `crmctl` с ключами, которых
  владелец не видел при подписи.

### 4.3. Здоровье и автооткат (`update`)

- Без изменений: кандидат рядом со старой версией, `/api/health` сразу после переключения и через 2 минуты,
  при сбое — `restoreVersion` на прежний тег, коды выхода 0/1/2.
- Добавляется: `worker` должен стать `healthy` по healthcheck compose (`docker inspect`) в пределах
  `--wait-seconds` после переключения и оставаться таким при повторной проверке. Иначе автооткат.
- `syncCli` выполняется только после успеха, как и сейчас. При автооткате хостовый `crmctl` не меняется.

### 4.4. `crmctl rollback`

- `state.json` дополняется полями `manifestSha256`, `kid` и `verified: "signature" | "stub"` у `current` и
  `previous`. Это добавление: старые записи без этих полей читаются.
- Перед переключением: `packages/<клиент>-<прежняя>/manifest.json` совпадает с `previous.manifestSha256`,
  подпись проходит проверку текущим доверенным набором, Id образа совпадает с `digest`, проходит проверка
  водяного знака (D-307). `images.tar` для отката не нужен, его можно удалить после `update`.
- Если ключ прежней версии отозван или запись о проверке отсутствует, на бою откат запрещён с сообщением
  «нужен пакет через `crmctl update`». На стенде разрешён с предупреждением.
- `crmctl` прежнего образа ставится на хост только тогда, когда его набор `releaseKeys` не шире текущего.
  Так откат не возвращает доверие к отозванному ключу. Иначе остаётся текущий `crmctl` и печатается
  предупреждение.

### 4.5. `CRM_VERIFY_STUB`

- В сборке с `CUSTOMER_ID` ветки заглушки **нет в коде**: её вырезает `define` при сборке `crmctl`. Тест
  проверяет, что в клиентском `dist/crmctl.mjs` нет строки `CRM_VERIFY_STUB`. Боевой сервер всегда ставится
  клиентской сборкой, поэтому на бою флаг ни на что не влияет.
- В общей сборке (стенд, локально) `CRM_VERIFY_STUB=allow` действует только при `CRM_STAND=1` в
  `/etc/crm/app.env`. Команда громко предупреждает, а в `state.json` пишется `verified: "stub"`.
- Когда стенд начнёт получать пакеты, подписанные `stage` (O4b), заглушка удаляется совсем (R8, §8).

### 4.6. Новые подкоманды

- `crmctl package verify <архив|каталог> [--sig F]` — только чтение. Печатает клиента, версию, `kid`,
  число файлов и итог. Код выхода 0 или 1.
- `crmctl keys [--json]` — вшитые ключи релизов (`kid`, sha256), на стенде ещё ключи `stage`. Ядро не нужно.

## 5. Конвейер

### 5.1. CI (`.github/workflows/release.yml`)

Тег `v*` (защищён) и вход `customer` → Environment `release` с одобрением владельца →
образ клиента (`CUSTOMER_ID`, `BUILD_ID`, `BUILT_AT`, секреты `license_keys`, `release_keys`) →
`check-image.sh` → `scripts/release-pack.ts` → артефакт `crm-<клиент>-<версия>.tar.zst` (хранение 7 дней).
В сводку прогона попадают sha256 архива, sha256 `manifest.json` и `releaseKeys`. Затем отдельная задача в
Environment `stage` подписывает тот же манифест ключом `stage` и выкладывает пакет на стенд
(`crmctl update`), после чего идут полный e2e и изоляция на этом пакете (ARCHITECTURE §8.2 п. 7).

### 5.2. `scripts/release-pack.ts` (CI, без ключей)

Собирает архив по §2 из образа и `deploy/`. Отказывает, если в путях есть `src/`, `*.ts`, `*.map`, `.env*`,
`*.pem`, `*private*`, или если копия миграций расходится с образом. Печатает sha256.

### 5.3. `scripts/release-sign.ts` (владелец, у себя, офлайн)

```
tsx scripts/release-sign.ts keygen --kid rel-2026a --out <путь вне репозитория>/release-private-rel-2026a.pem
tsx scripts/release-sign.ts pubkey --key <файл>
tsx scripts/release-sign.ts sign <архив> --key <файл> --kid rel-2026a --expect-sha256 <из сводки CI> [--known-keys <файл>]
tsx scripts/release-sign.ts verify <архив> [--sig F] --pubkey <base64>
```

- `keygen` — файл 0600, не перезаписывается; на экран выводятся `kid` и открытый ключ для `release_keys`.
  Если путь внутри рабочего дерева git, команда отказывает.
- `sign`:
  1. Сверяет sha256 архива с числом из CI, которое владелец переписывает сам со страницы прогона.
  2. Проверяет весь архив тем же читателем, что и `crmctl` (§4.1, шаги 2–4, без записи на диск).
  3. Показывает сводку: клиент, версия, `commit`, `builtAt`, схема, `minFromVersion`, Id образа, число файлов
     и `releaseKeys` с отпечатками.
  4. Если в `releaseKeys` есть ключ, которого нет в локальном `--known-keys` владельца, отказывает без
     `--accept-new-key`.
  5. Просит ввести версию для подтверждения.
  6. Пишет `<имя>.manifest.sig` и печатает sha256 архива, которую нужно передать при первой установке (§6).
- Утилита не содержит ключей и ничего не отправляет в сеть. В образ поставки она не входит, ядро ей не нужно.

## 6. Первая установка: якорь доверия

Пока `crmctl` на сервере нет, его берут из самого пакета, поэтому подпись на этом шаге ничего не доказывает.
Якорь доверия — sha256 архива. Владелец передаёт его root ЦРП отдельным каналом: лично или голосом, но не
тем каналом, которым пришёл архив.

1. Root: `sha256sum crm-<клиент>-<версия>.tar.zst` совпадает с числом от владельца — **до распаковки**.
2. Распаковка, затем `./install.sh --package <каталог>`. После копирования `crmctl` скрипт запускает
   `crmctl package verify` и `crmctl keys`. Если проверка не прошла, скрипт удаляет копию `crmctl` и
   выходит с кодом 1.
3. Владелец сверяет отпечатки из `crmctl keys` со своими. Дальше все обновления проверяет уже
   установленный `crmctl` (§4).

## 7. Тесты (исправление начинается с падающего теста)

- Unit, читатель архива: симлинк, жёсткая ссылка, устройство, pax/GNU-заголовок, `..`, абсолютный путь,
  повтор, `manifest.json` не первым или больше предела, обрезанный архив. Каждый случай отвергается.
- Unit, подпись: верная проходит. Отвергаются: изменённый байт манифеста, подпись без префикса,
  неизвестный `kid`, `stage-*` без `CRM_STAND`, `rel-*` из файла ключей стенда, лишний, отсутствующий или
  изменённый файл, чужой клиент. Ключи — `generateKeyPairSync('ed25519')` в самом тесте.
- `update` и `install`: при плохой подписи `exec` не вызывается ни разу, `etc/`, `compose/` и `state.json`
  не меняются, `.incoming-*` удалён. Несовпадение `releaseKeys` с `crmctl` образа — стоп до миграций.
  `worker` не здоров после переключения — автооткат.
- `rollback`: подменённый Id образа, изменённый сохранённый манифест, отозванный ключ — отказ на бою.
- Сборка: клиентский `dist/crmctl.mjs` не содержит `CRM_VERIFY_STUB`, сборка с `test-*` или `stage-*` в
  `release_keys` падает. Статический тест: в репозитории нет `BEGIN … PRIVATE KEY` и файлов `*-private*`.
- Стенд, приёмка O4c: пакет с подписью `stage` → `update` → пакет с намеренно нездоровым `app` →
  автооткат → `rollback` туда и обратно → пакет с изменённым байтом и пакет с чужим ключом отвергнуты.

| В-1 | Ключи релизов | Два ключа, `rel-2026a` и резервный `rel-2026b`. Создаёт владелец на своём ноутбуке (`release-sign keygen`). Закрытые половины — в двух зашифрованных офлайн-копиях, резерв отдельно от основного. Не в облаке, не в мессенджерах, не на серверах |
| В-2 | Ключ стенда | Хранить секретом GitHub Environment `stage` без одобрения. На стенде лежит его открытая половина в `/etc/crm/stage-keys.json` |
| В-3 | GitHub | Environment `release` с обязательным одобрением владельца и защита тегов `v*`. Настраивает владелец: у агентов на это нет прав |
| В-4 | sha256 при первой установке | Владелец передаёт её root ЦРП лично или голосом, не тем каналом, которым пришёл архив |
| В-5 | Provenance сборки (attestations GitHub и Sigstore — зарубежный сервис, метаданные без ПДн) | Не сейчас, вернуться после пилота |
