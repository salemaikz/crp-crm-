# Журнал решений

Нетривиальные решения по продукту: что решили, почему, что отвергли. Новые
записи — **сверху**. Формат записи:

```
## D-NNN · YYYY-MM-DD · Заголовок
Статус: принято | предложено (ждёт владельца) | отменено (см. D-MMM)
Решение. Одно-два предложения.
Почему. Ключевые причины.
Отвергли. Варианты и почему нет.
```

`предложено` — решение architect, действует как значение по умолчанию, пока
владелец не подтвердил или не отменил; агенты не считают его неизменным.
`предложено (ждёт владельца)` — нужен ответ владельца, до ответа работаем по
рекомендованному варианту. `принято` — нормативно: расхождение кода с ним — баг.

Подробности решений: `docs/ARCHITECTURE.md`, `docs/CONFIG.md`,
`docs/INTEGRATIONS.md`, `docs/PROCESS.md`.

## D-137 · 2026-10-20 · Запись: что откладывается на миграции и B3b
Статус: предложено
Решение. Причина отмены `not_target` (эффект ядра `cancel_future` при «Не целевой» и проигрыше сделки по
жёсткой причине) добавляется миграцией M1 `bookings_cancel_reason_check` (расширение закрытого списка, только
добавление; файл оформляет координатор, `docs/booking-design.md` §12). Перенос мероприятия на другую дату или
время вместе с записями и задачами «Сообщить о переносе» — B3b с миграцией M2 (`tasks_source_check` +
`event_moved`); в B2 дата и время меняются только у мероприятия без записей, иначе 409 `event_has_bookings`.
Почему. Схема v1 не принимает причину, которую уже выпускает ядро; задача о переносе требует нового источника
задач, а B2 — репозиторий и API.
Отвергли. Писать `client` вместо `not_target` — отчёт причин отмен потеряет «не целевой»; задачи о переносе
с источником `manual` — без `source_key` они задвоятся при повторе.

## D-136 · 2026-10-20 · Запись: права и охваты действий
Статус: предложено (уточняет D-072, D-075)
Решение. Создать, перенести, подтвердить и отменить групповую запись — `booking.create` **по роли** (`scopeOf`),
а не по отношению: консультант по `booked_with_me` групповые записи не трогает. Явка — `booking.attend` (РОП;
дежурный — `duty_today`, только своё мероприятие сегодня; оператор без дежурства — нет). «Пришёл → Не пришёл»
после суток мероприятия — только при `booking.manage`. Серии, разовые мероприятия, правка и отмена
мероприятия, дежурные — `booking.manage`. Новая запись — только для карточки, видимой по `booking.create`.
Места мероприятия («осталось N из M») считаются по всем записям без охвата записей: наружу выходит только
число. Список гостей — строки по охвату `booking`; имя, контакт и 4 последние цифры номера — проекция без
охвата клиента (как D-072).
Почему. PROCESS 8.2: явка у оператора — конфликт интересов, запись консультанта — «к себе»; оператор должен
видеть свободные места, не видя чужих записей.
Отвергли. Отдельное право `booking.cancel` — правка каталога и пресетов ради действия, которое уже покрывает
«управлять своей записью» (`booking.create`); места по охвату — оператор видел бы «30 из 30 свободно».

## D-135 · 2026-10-20 · Серии: лишние мероприятия «снимаются», а не удаляются
Статус: предложено
Решение. Синхронизация серии (`booking.planSeriesSync`) идёт сразу при правке серии РОП и задачей
`events-ensure`; серия блокируется `FOR UPDATE`, число записей и дежурных читается после блокировки её
мероприятий. Нетронутое мероприятие, которое серия больше не порождает, получает `status = 'cancelled'` и
`occurrence_key = NULL`: ключ освобождается, и возврат дня недели создаст мероприятие снова. Отменённое РОП
сохраняет ключ и не возвращается. Разовое мероприятие — `series_id NULL`, `id` = ключ запроса. Дежурные по
умолчанию не создаются: РОП отмечает явку своим охватом.
Почему. У `crm_app` нет `DELETE` на `events` (D-068, schema-v1); отменённое с ключом навсегда заняло бы дату.
Отвергли. Выдать `DELETE` на `events` — мероприятие могло бы исчезнуть вместе с историей, на которую
ссылаются записи; оставлять ключ у снятых — правка серии туда и обратно теряла бы мероприятия.

## D-134 · 2026-10-20 · Запись и сделка: сделку обеспечивает сама запись, идемпотентно
Статус: предложено
Решение. Создание записи под блокировкой карточки вызывает `deals.ensureOpen`: открытая сделка клиента в
воронке с `createDealOn: agreed` или новая на этапе `auto = on_agreed` (`request_id` = ключ записи); `deal_id`
пишется в запись, перенос его сохраняет. Нет такой воронки — сделки нет. Эффекты сделок из машины карточки
исполняет `deals/effects.ts` (в B2: `ensure_open`, `advance` только вперёд, `set_needs_rebook`,
`lose_created_by`; остальное — B6). «Пришёл» при карточке не в `agreed` двигает сделку напрямую.
Почему. Запись из карточки в `agreed`/`client` не порождает события карточки, а этап «Записан» нужен; при
итоге «Договорились» эффект `ensure_open` находит ту же сделку — двойного создания нет.
Отвергли. Сделка только через эффект итога — запись повторной продажи (`client`) осталась бы без сделки.

## D-133 · 2026-10-20 · Запись и карточка: карточку меняет только машина обзвона через порт
Статус: предложено (уточняет D-049)
Решение. Модуль записи не пишет `cards`. Новая запись и перенос — только для карточки в `agreed` или `client`;
иначе 409 `outcome_required`: интерфейс открывает итог «Договорились», и C5 вызывает тот же `createBooking` в
своей транзакции (`fromOutcome`). «Передумал» после отмены — новая запись тем же путём; переход
`cancelled → registered` API не открывает. Последствия статусов — события ядра `calling` через `CardPort`
(реализует calling): `no_show`, `attended`, `booking_cancelled`, `attendance_corrected`, `attendance_sweep`;
отмена мероприятия = `booking_cancelled` с причиной `client` (в записи — `event_cancelled`). Событие
вызывается, только если состояние карточки его допускает; отказ ядра (`stale`) не отменяет действие с
записью, а пишется в `booking_history.meta`.
Почему. Одна машина состояний (D-013) и инвариант «Договорились всегда со следующим шагом» (D-049); запись в
обход итога давала бы `callback` с активной записью, без сделки и с открытой задачей «перезаписать».
Отвергли. Менять карточку SQL-ем модуля записи — чужая зона и вторая копия переходов № 16–18, 31; отдельное
событие ядра для отмены мероприятия — те же эффекты, что у `booking_cancelled: client`.

## D-132 · 2026-10-20 · Запись: идемпотентность по ключу запроса и `opId` истории
Статус: предложено
Решение. Создание и перенос — `bookings.request_id` (UUID мастера): проверка после блокировки карточки; тот же
клиент и мероприятие → прежний результат с `replayed: true`, иначе 409 `request_reused`. Действия со статусом
несут `opId` и `version`: `booking_history.id = opId`; строка уже есть → текущая запись без повторных
эффектов; затем сравнение `version`. Отмена мероприятия идемпотентна по состоянию. Серия и разовое
мероприятие — `id` = ключ запроса, `ON CONFLICT (id) DO NOTHING`.
Почему. Повтор после обрыва сети не создаёт вторую запись и не задваивает задачи и события карточки; схема
v1 не меняется.
Отвергли. Отдельная таблица ключей запросов — миграция ради того, что дают существующие уникальные индексы;
только `version` — повтор после успешного ответа получал бы ложный 409.

## D-131 · 2026-10-20 · Запись: блокировки и гонка за последнее место
Статус: предложено
Решение. Порядок блокировок во всех путях записи: карточка (блокировка клиента в пространстве, PROCESS 12.18)
→ мероприятие `SELECT … FOR UPDATE` → записи. Число занятых мест — `COUNT(*)` записей в статусах, держащих
место, **отдельным запросом после** блокировки мероприятия (READ COMMITTED видит всё зафиксированное);
решение — `booking.eventBookability`. Каскад по мероприятию сначала блокирует карточки по возрастанию `id`.
Внешняя транзакция повторяется до 3 раз при `40P01`/`40001`; внутри чужой транзакции (C5) — без повтора.
Вторая из двух одновременных записей на последнее место получает 409 `event_full` со списком ближайших
мероприятий с местами.
Почему. PROCESS 12.19; одна точка сериализации на мероприятие без изменения схемы; единый порядок
исключает взаимные блокировки с итогом «Договорились», который сначала блокирует карточку.
Отвергли. Счётчик `events.taken` с `CHECK (taken <= capacity)` — миграция и второй источник правды, который
расходится при каскадной отмене и импорте; SERIALIZABLE — повторы на всех путях; advisory lock по
мероприятию — та же сериализация, но не видна в SQL и не сериализует правку вместимости.

## D-101 · 2026-10-20 · K0: ядро `@crm/core` — внешний обфусцированный пакет Next 16
Статус: предложено (K0 сошёлся; вопрос В-1 о достаточности такой защиты по-прежнему у владельца, D-028)
Решение. `packages/core/build.mjs`: esbuild (один файл CJS, минификация, без карт, `zod` внешний, константы
водяного знака `__CRM_CUSTOMER_ID__` и `__CRM_BUILD_ID__` через `define`) → javascript-obfuscator 5.9.0
(переименование идентификаторов включая верхний уровень, строковый массив с порогом 0,5 без шифрования,
перестановка потока с порогом 0,3; без self-defending, debug-protection и мёртвого кода; фиксированный
seed — одинаковый вход даёт одинаковый файл) → `packages/core/dist/index.cjs` (в `.gitignore`).
`@crm/core` — рабочее пространство npm, `exports` → `dist/index.cjs`. `npm run build` сначала собирает
ядро. В production-сборке `next.config.ts` объявляет `@crm/core` внешним (`commonjs`) только для сервера
Node.js; подпуть, клиентская сборка и edge роняют `next build`; исходники ядра исключены из трассировки
standalone. В dev и тестах ядро — исходники через paths `tsconfig.json`. Слой клиента заменяет один файл
`dist/index.cjs`, собранный с `--customer` и `--build-id`, без повторного `next build`.
`CRM_CORE_BUNDLE=1` — запасной вариант D-028 (ядро в бандле Next, только минификация) без правки кода.
Проверено 20.10 на зонде (zod, классы с приватными полями, генераторы, async, Intl, RegExp): `next build`
проходит; `/api/health` и маршрут с ядром отвечают в `next start` и в `.next/standalone` (в том числе
перенесённом в другой каталог и с подменённым ядром клиента); в standalone нет исходников ядра, `*.ts`
и `.map`; тесты ядра, собранные тем же конвейером, зелёные на обфусцированном коде (`build.mjs --check`);
`tsc`, lint и unit зелёные. Замеры: сборка ядра — доли секунды (≈ 0,7 с на 100 КБ минифицированного
кода), `next build` ≈ 31 с как без ядра; файл больше в 1,2–2,2 раза; горячий путь медленнее ≈ на 15–20 %.
Почему. Ядро не бандлится в чанки Next, поэтому водяной знак клиента — один файл в слое образа, а
обфускатор не трогает RSC и server actions. Рабочее пространство даёт настоящий `node_modules/@crm/core`
и для `next start` (e2e), и для standalone без копирования руками.
Отвергли. Алиас на `dist` с бандлингом в чанки Next — работает, но водяной знак требует `next build` на
каждого клиента. `serverExternalPackages: ['@crm/core']` — Next запрещает пакет одновременно в
`transpilePackages`, нужном в dev; явный `externals` проще и проверяем. ESM-файл ядра — `require(esm)`
зависит от версии Node 22; CJS работает везде. Ограничения: имена экспортов ядра читаемы (это его API);
тесты ядра в `--check` собираются вместе с кодом ядра, а не импортируют сам `dist/index.cjs`.
## D-075 · 2026-10-21 · Роли первого клиента: дежурство — у оператора и консультанта, поля — только CLI
Статус: предложено (ждёт владельца: кто может дежурить)
Решение. Раздел ролей пресета клиента — отдельный слой `presets/clients/<клиент>/roles.json`
(`{ global: { roles } }`), матрица PROCESS 8.2 переведена так: оператор — «своё» без `client.edit_identity`;
РОП — пространство на всё, кроме приёма и назначения передач и `settings.fields`; консультант —
`booked_with_me {-1, 30}` со всеми пятью действиями плюс свои задачи и отчёт; директор — `readOnly`, чтение
пространства, `report.export`, `data.export_all`; руководитель отдела — `handoff_to_my_team`, отчёт по команде;
маркетолог — `handoff_assigned_to_me`. Отношение `duty_today` (дежурство) есть у оператора и консультанта:
назначить дежурным сотрудника другой роли можно, но прав на гостей он не получит. `settings.fields` не выдан
никому: до 1.11 поля меняются только через CLI (CONFIG §5). Окно консультанта задаётся параметрами отношения;
ключ пространства `access.consultantWindow` (CONFIG §6.9) доступом не читается.
Почему. Дежурство — назначение, но права дают только отношения роли; кто дежурит у клиента, документы не
говорят. Один источник окна консультанта, иначе две настройки разойдутся.
Отвергли. `duty_today` у всех ролей — маркетинг получил бы гостей мероприятия без решения клиента;
`settings.fields` РОП — редактора нет, а право на будущее открывает его молча.

## D-074 · 2026-10-21 · Обёртки: мутация — пишущее разрешение; 423 раньше проверки права; страницы — 404
Статус: предложено
Решение. Порядок обёртки: Origin (мутирующий метод route; у server actions — проверка Next) → сессия →
Viewer → блокировка → разрешение → обработчик → аудит. Мутация = мутирующий метод и пишущее разрешение (или
`authenticated`/`admin`); поиск POST-ом и выгрузки мутацией не считаются и работают в «только чтении».
Блокировка (роль `readOnly`, лицензия `read_only`/`invalid`/`missing`) проверяется до разрешения: 423 одинаков
для любого id и ничего не выдаёт; `securityMutation` — ключ закрытого списка D-054 в ядре. Нет права: 404 для
объекта, 403 для раздела; страницы отвечают `notFound()` и на раздел. Ответы API — `{error: код}` без текста,
`Cache-Control: no-store`; в лог необработанной ошибки — имя, код и сообщение без `detail` Postgres. Маршруты
без сессии — `publicRoute({reason, origin})`. Аудит обёртки — после успеха; аудит, который должен быть атомарен
с изменением, модуль пишет в своей транзакции.
Почему. Директор и лицензия «только чтение» должны получать 423 на любую мутацию (ARCHITECTURE §5.3), а не
404/403 в зависимости от объекта. `forbidden()` в Next 16 экспериментален (нужен `authInterrupts`).
Отвергли. Мутация «по методу» — поиск и выгрузка POST-ом ломались бы в «только чтении»; явный флаг
`mutation: false` в обёртке — им легко выключить блокировку настоящей мутации.

## D-073 · 2026-10-21 · Viewer: собирается из БД на каждом запросе, плохие настройки ролей — отказ
Статус: предложено
Решение. `buildViewer()`: `getSession()` → `users` (не `active` — 401) → активные членства во включённых
пространствах (по умолчанию — пространство `is_default`) → роль по `role_key` из `global.roles` текущей ревизии
(свой Zod поверх `getActiveConfig()`; ожидаемая форма `{ rev?, global: { org: { timezone }, roles } }`). Роли нет
в настройках или она архивная — сотрудник без прав. Раздел ролей не проходит схему и валидатор — исключение
(500), а не «пустые права по умолчанию». `team` без команды сужается до `own`. `today` — местная дата `now` в
поясе `global.org.timezone`. Viewer и SystemActor заморожены и зарегистрированы (WeakSet): scopeSql отклоняет
объект той же формы, собранный руками. SQL сборки — `src/server/access/repo.ts` (исключение из «SQL только в
`domain/*/repo.ts`»: доступ не может зависеть от домена). Подмена сессии, настроек, лицензии и часов — только в
тестах (`access/testing.ts`, в production бросает); лицензия до P10 — заглушка `valid`.
Почему. Кэша прав нет (ARCHITECTURE §5.2 п. 1): отключение и смена роли действуют со следующего запроса.
Ошибка в пресете не должна тихо давать или отнимать доступ.
Отвергли. Кэш Viewer на сессию — передача клиента и отключение действовали бы с задержкой; роль по умолчанию
при ошибке настроек — fail open.

## D-072 · 2026-10-21 · Охват сущностей: всё через карточку; отношения — по живым записям и передачам
Статус: предложено (уточняет D-016)
Решение. Клиент, контакты, номера, сделки, записи, звонки, заметки и чаты видны, если видна карточка клиента
в том же пространстве; лента — также по карточке клиента, в которого он слит (цепочка `merged_into_id`, D-068).
Задачи: `own` — исполнитель я и карточка видна; `team`/`space`/`all` — по охвату роли. Отношения: окно
консультанта — его индивидуальная запись (`resources.user_id = я`) со статусом `registered|confirmed|attended|
no_show` и `booking_date ∈ [today − toDays, today − fromDays]`; `booking.attend` консультанта — только своя запись
в окне, а не любая запись клиента; `duty_today` открывает только записи и мероприятие своего дежурства сегодня,
но не карточку и не клиента (имя, компания и хвост номера гостя — проекция списка гостей); отношения передач —
передача `pending|accepted` в команду, где я руководитель (или исполнитель), команда — в моём пространстве;
отклонённая и отменённая передача доступ закрывает. Пишущее разрешение у `readOnly` — FALSE и в SQL.
Почему. Один предикат на карточку — одна точка ошибки; передача клиента снимает доступ ко всему сразу.

## D-083 · 2026-10-21 · Ревизии настроек: хэш канонического JSON, номер по всем версиям, миграция в памяти
Статус: предложено (уточняет D-060)
Решение. `config_revisions.hash` = sha256 канонического JSON документа (ключи по алфавиту, без пробелов),
считается WebCrypto в ядре. Номер новой ревизии = максимум `rev` области по **всем** версиям схемы + 1.
Геттер берёт последнюю ревизию со `schema_version ≤` версии сборки; если она младше, приводит её
миграцией в памяти, а пишет мигрированную ревизию только шаг `crmctl update`. Запись: одна
advisory-блокировка на все области, проверка набора целиком, `expectedRev` → 409, повтор с тем же хэшем
(и тем же `preset_doc`) ревизию не создаёт. Кэш процесса сверяет головы не чаще раза в 5 с.

Отвергли. Хэш через `node:crypto` (ядро тогда не работает в браузере); блокировка на область (записей
мало, а проверка набора всё равно читает все области).

## D-082 · 2026-10-21 · Слияние слоёв по содержимому массива; обновление пресета — трёхстороннее по листьям
Статус: предложено (уточняет D-061)
Решение. Массив сливается по `key`, если все элементы обоих массивов — объекты со строковым `key`; по
`date`, если у всех вместо `key` есть `date`; иначе заменяется целиком. `null` — значение, отсутствие
ключа — «не менять», пустой массив с ключом ничего не удаляет. Смесь, повтор ключа, `__proto__` —
ошибка. Обновление пресета (`presetUpdate`) идёт по листьям: элементы массивов с ключом — по ключу,
массив без ключа — один лист; лист применяется, только если текущее значение равно значению прошлого
`preset_doc`, иначе попадает в `kept` («оставлено как у клиента»), с `--force` — в `forced`.
Почему. Одно правило без реестра путей: новый список с `key` сливается правильно без правки кода; правка
РОП одного поля итога не блокирует обновление остальных полей того же итога.
Отвергли. Реестр путей «какой массив по какому ключу» — забудут дополнить; сравнение по целым разделам —
одна правка блокирует всё обновление раздела.

## D-094 · 2026-10-21 · Приглашение и сброс — ссылка с токеном во фрагменте, выдаёт администратор

## D-093 · 2026-10-21 · Перебор: задержка по номеру до 30 с, блок по IP по числу неудач
Статус: предложено (уточняет CONFIG §6.16 `security.loginAttempts`)
Решение. После `perPhone` неудач по номеру за `windowMin` каждая следующая попытка возможна не раньше
`1 с · 2^(n − perPhone)`, но не позже 30 с; до этого — 429 без проверки пароля и без счёта. IP
блокируется до конца окна после `perIp` **неудач** (успешные входы не считаются); неизвестный IP — общее
ведро `perIp × 5`. Успех сбрасывает счётчик номера, но не IP. Нет номера, неверный пароль, отключён, нет
пароля — один ответ `invalid`, bcrypt считается всегда. Состояние — в памяти процесса
(`auth/throttle.ts`). Пароль: ≥ 8 символов, ≤ 72 байт, не из списка частых, не повтор одного знака, не
номер сотрудника.
Почему. Блокировка учётки позволила бы чужому запереть оператора (CONFIG §6.16). Офис ЦРП выходит в сеть
через один адрес: счёт всех попыток по IP запер бы утренний вход 20+ сотрудников. Предел 30 с ограничивает
и перебор (~2 попытки в минуту на номер), и неудобство жертвы, если её номер держат в задержке.
Отвергли. Задержка по паре (номер, IP) — распределённый перебор её обходит; ожидание на сервере (`sleep`) —
держит соединения и не мешает параллельным запросам; хранение счётчиков в БД — лишняя запись на каждую
попытку при одном процессе (ARCHITECTURE §1, «Лимиты входа»).

## D-091 · 2026-10-21 · Сессия — непрозрачный токен в cookie, sha256 в БД, скользящий срок
Статус: предложено (уточняет D-006 «своя session-auth»)
Решение. Cookie несёт 32 случайных байта base64url; `sessions.id` = sha256 hex токена. Подписи и
`SESSION_SECRET` нет. Срок скользящий: `expires_at`/`last_seen_at` продлеваются не чаще раза в час;

добавляет, а секрет — лишний ключ установки; копия БД или бэкап не дают рабочих cookie. `Secure` по

стеком; cookie без срока (сессионная) — PWA на iOS теряет её при выгрузке приложения.

(`created_by`, `*_by`, `actor_id`, `author_id`, `calls.user_id`, `bookings.booked_by_user_id`) допускают `NULL` —
это система, CLI (`crmctl`: первый администратор, сброс пароля), импорт или воркер. `NOT NULL` остаётся только у
субъекта строки (сессия, членство, получатель уведомления, консультант, дежурный, отсутствующий) и у действий,
возможных лишь с устройства сотрудника (`skips`, `proposals`, `phone_probes`). Звонок без автора — только при
`via` `import` или `telephony` (`calls_user_id_check`). Сущности не удаляются (отключение, архив,
`merged_into_id`), поэтому `ON DELETE` не задан, кроме `sessions` (каскад от пользователя).
Почему. Эскиз §4.3 ставил FK выборочно; ссылку на несуществующего клиента, карточку или сотрудника должна
ловить БД, а не отчёт через неделю. Цена — порядок вставки в тестах и сидах, она мала. Импорт «Подтвержден»
(векторы K1d r30a–r30c) пишет звонок и сделку от имени системы: с `NOT NULL` у автора он падал бы на `INSERT`
или требовал выдуманного автора, который исказил бы статистику оператора.
Отвергли. Составные FK `(space_id, id)` для согласованности пространства — лишняя сложность при одном
пространстве; согласованность держат репозитории и прогон изоляции.

без имени и хэша файла. Ключ состояния = хэш колонок итога, ЛПР, статуса, ниши, заметки. Та же пара
ключей → пропуск. Изменился ключ состояния, карточку в CRM не трогали (`touched_in_crm = false`) → один
импортный звонок с `import_key = ключ строки + ключ состояния`, состояние обновлено. Трогали → «оставлено
как в CRM» и строка на разбор РОП. Номер один не годится как ключ: в таблицах ЦРП 45 номеров общие у
разных компаний.
Почему. «Файл + хэш справочных полей» не видел правку итога в таблице (перезвон терялся), а ключ от sha256
файла задваивал все импортные звонки.
Отвергли. Ключ «профиль + номер или БИН» (предложение ревью) — склеивает разные ТОО с общим номером; БИН в
таблицах ЦРП нет.
